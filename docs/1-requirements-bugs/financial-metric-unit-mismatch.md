# 财务指标单位错配（R001 SQL 结果格式化器）— 核查报告

- 核查时间：2026-09-19
- 触发：李工质询「L1-001 与 L1-002 的单位不一致，是答案错了还是 PostgreSQL 存错了？」
- 结论：**PostgreSQL 存的值是对的，展示层（`sql-result-formatter.ts`）错了。** 根因是财务五表 schema 没有单位列，格式化器只能按数值量级"猜"单位。
- 状态：**待修（P0）**。未改动任何代码。

---

## 一、问题定性

| 层 | 是否正确 | 说明 |
|---|---|---|
| 源 PDF（年报） | 正确 | 各公司年报印刷单位不同 |
| 抽取器 → PostgreSQL | **数值正确，但口径不统一** | `revenue numeric` 等裸数值列；落库单位沿用各自源文档，**元 / 千元 / 百万元三种混用** |
| DB schema | **缺列** | 五表均无 `unit` / `currency_unit` 列（`drizzle/r001_financial_tables.sql`） |
| `sql-result-formatter.ts` | **错误** | `detectMonetaryUnit()` 按「本批返回值的最大绝对值」猜单位 |
| 最终答案 | 错误 | 猜错时整体缩 1000 倍 |

### 各公司实际落库口径（由 `fix_testset_data_source.py` 的 `VERIFIED_METRICS` hints 反推）

| 公司 | 落库口径 | 证据（hints） |
|---|---|---|
| 中国能建 | 千元 | `"4,529.30"` / `"452,929,608"` → 4529.30 亿 × 1e5 |
| 中国铁建 | 千元 | `"10,297.845"` / `"1,029,784,460"` → 10297.84 亿 × 1e5 |
| 江苏银行 | 千元 | 总资产展示 49.31 亿 ⇒ 原始 4.93e9，= 49313.16 亿千元 |
| 五粮液 | **元** | `"40,528,509,770.23"` → 405.29 亿 元 |
| 格力电器 | **元** | `"171,118,161,275.41"` → 1711.18 亿 元 |
| 中国长城 | **元** | `"15,808,600,064.94"` → 158.09 亿 元 |
| 片仔癀 | **元** | `"9,001,411,806.06"` → 90.01 亿 元 |
| 中国人保 | **百万元** | OCR 来源，营收原始 669,044（百万） |

⇒ 同一张表里三家千元、四家元、一家百万元。**格式化器却拿一个全局阈值去猜**，必错。

### 铁证（中国铁建 营业收入）

```
DB 实测值（V13-r5 报告 answer 字段留痕）：1,029,784,460
GT（qa-golden.json）：                    10,297.84 亿元
换算校验：1,029,784,460 千元 × 1000 = 1.02978446e12 元 = 10,297.8446 亿元  ✅ 对得上
```

`scripts/fix_testset_data_source.py` 的 `VERIFIED_METRICS` 同样记录：
`"营业收入": {"yi": 10297.84, "hints": ["10,297.845", "1,029,784,460"]}` → 千元口径。

**所以库里没错，是格式化器把千元当成了元。**

## 二、根因：按量级猜单位，硬门槛在 1e9

`src/server/rag/query/sql-result-formatter.ts:144-170`

```ts
if (maxVal > 1e9) return { unit: "元",   divisor: 1e8 };
if (maxVal > 1e5) return { unit: "千元", divisor: 1e5 };
return               { unit: "万元", divisor: 1e4 };
```

`maxVal` 取的是**本次查询返回的所有货币字段**的最大绝对值。所以判定结果不取决于公司，
只取决于「这家公司某个字段在千元口径下有没有越过 10 亿（= 1 万亿元）」：

| 公司 | 存储口径 | 代表值（千元） | 是否 > 1e9 | 猜出的单位 | 结果 |
|---|---|---|---|---|---|
| 中国能建 | 千元 | 总资产 941,597,382 | 否（9.42e8） | 千元 ✅ | 9415.97 亿 **正确** |
| 中国铁建 | 千元 | 营业收入 1,029,784,460 | **是**（1.03e9） | 元 ❌ | 10.30 亿 **错 1000 倍** |
| 江苏银行 | 千元 | 总资产 4,931,316,000 | **是** | 元 ❌ | 49.31 亿 **错 1000 倍** |

### 决定性证据：同一家公司被贴了两种单位

按 55 条评测样本统计上下文头部的「数据单位」标注：

```
江苏银行   元 / 千元   <<< 同一家公司、同一份年报，两种单位
```

单位若真是数据的属性，同一家公司不可能同时是「元」和「千元」。
唯一解释：**它是按查询返回了哪些字段临时猜的**。

其余公司单位标注：东吴证券(元)、中国人保(千元)、中国能建(千元)、中国铁建(元)、
中国长城(元)、五粮液(元)、华海药业(元)、格力电器(元)、片仔癀(元)。

`sql-result-formatter.ts:19` 的注释写着「已验证：10 家样本公司均正确」——
**该验证结论不成立**，中国铁建、江苏银行、中国人保三家都在错。

## 三、影响面（55 条样本逐条归因）

| 类别 | 条数 | 条目 |
|---|---|---|
| 数值正确 | 32 | L1 多数、L3 多数 |
| **单位换算错（1000 倍）** | **10** | 中国铁建 L1-002 / L1-012 / L3-005 / L3-015、江苏银行 L1-025 / L3-006、中国人保 L1-003 / L1-013 / L1-028 / L3-009 |

- `sql_formatted_ratio = 1.0`，55/55 走 SQL 短路，所以**单位错会 100% 直传到答案**。
- 单位错的 10 条同时打掉 **NA 与 CR** 两个指标（数值错 → NA 判 0；上下文无该数字 → CR 判未覆盖）。
- 修复后 NA 上限可从 0.50 回升至约 0.68（10 条里 26 满分 + 1 半分口径重算）。

## 四、李工判断的核对

### 「没有数据是正常的，评估器要确定数据范围，和年报相呼应」

**方向对，但这 55 条不是这个原因造成的。** 实测：

- 55 条问的**全部是 2025 年年度报告**；库覆盖的正是 `2025 年报 + 2026 Q1` → **范围对齐**。
- 没有一条是因为「超出存储时间窗」而缺数。
- 真正的缺口是上表那三类：单位错 10 条 + 字段漏抽 2 条。
- 但李工提的**机制问题真实存在**：`qa-golden.json` 的 GT 未标注「该值应落在哪张表 / 哪个口径」，
  评估器无法区分「库里没有」与「抽取漏了」。**评估集需要加一列数据范围/口径声明**，
  这是独立于单位 bug 的一项改造。

### 「6 家公司数据都比较准确，扩大公司范围没道理不准确」

**恰恰相反——扩大范围会更多踩坑。** 出错的开关是「千元口径下有没有超过 1e9」，
即营收/总资产有没有到**万亿元级**。中国能建（总资产 9416 亿）不越线 → 对；
中国铁建（营收 1.03 万亿）、江苏银行（总资产 4.93 万亿）越线 → 错。
而**越大的公司、越多的银行/保险**，越容易越线。同时各年报印刷单位混用
（格力电器/五粮液/片仔癀存「元」，中国能建/中国铁建存「千元」，中国人保存「百万元」），
所以「换个公司就不准」是必然，不是偶然。

另：结构化财务表现在**只有 10 家公司**（抽取日志 `批量处理完成: 总计=10`），
`data/financial_reports/2025_annual/` 下约 990 份 PDF 未做结构化抽取。
所以真要扩大覆盖，先补单位列，再谈批量抽取。

## 五、修复方案（二选一，待批准）

**方案 A（推荐）：抽取侧彻底归一。**
抽取器落库前把货币值统一换算为「元」。改动在 `data_service/pdf_extractor.py` 一侧，
`sql-result-formatter.ts` 的 `detectMonetaryUnit()` 整段删除，固定除以 1e8。
- 优点：从源头消除歧义，**不依赖任何猜测**；10 家重抽即可验证。
- 代价：需重跑 10 家 × 3 表抽取，并核 GT。

**方案 B：加单位列。**
`financial_income / _balancesheet / _cashflow / _indicators` 各加 `currency_unit varchar(8)`，
抽取时写入，格式化器读列不再猜。
- 优点：保留原始口径，可追溯。
- 代价：改 schema + 迁移 + 改抽取 + 改格式化器，改动面更大。

无论选哪个，`sql-result-formatter.ts:13-19` 的「量级启发式」注释与
`__tests__/sql-result-formatter.test.ts:55-70` 的用例都要一并改写——现在的单测把
**错误行为当成了正确预期**（`revenue: "452929608.0"` 断言出「千元」，实际应固定为元口径）。

## 六、附带核查：NA 分级断崖与 GT 释义

### NA 的三档分级没有中间层

`_pair_score()`（`unified_evaluation.py:180-190`）：相对误差
`<0.1% → 1.0` / `<1% → 0.5` / `≥1% → 0.0`。

所以「0.5 分」只覆盖 `[0.1%, 1%)` 这一条窄带，带宽 0.9 个百分点；
一过 1% 就断到 0，不再区分差多少：

| 样本 | GT | 答案 | 相对误差 | 得分 |
|---|---|---|---|---|
| L4-009 东吴证券 净利润同比 | 50.12% | 49.52% | **1.197%** | 0 |
| L1-002 中国铁建 营业收入 | 10297.84 亿 | 10.30 亿 | **≈99900%** | 0 |

差 1.2% 和差 10 万倍拿一样的 0 分——这就是「断崖」。
实测分布 `26 条满分 / 1 条半分 / 28 条零分`，印证了没有中间梯度。

### GT = ground truth（标准答案）

`scripts/qa-golden.json` 里每条 query 的 `expectedAnswer` 字段，
由人工依据年报原文核对后写入，是评测的**唯一参照**。
L3 计算推理类（如毛利率）的 GT 写成
「毛利率约 12.2%，根据营业收入约 4529.30 亿元和营业成本约 3977.11 亿元计算得出」——
把**计算依据也算成了必须答出的数值**。答案只报结论 12.2%，
另外两个数值必然配对失败 → **L3 类 NA 结构性地不可能满分**（实测均值 0.0667）。
这是 GT 写法问题，需要在 NA 口径上区分「结论值」与「依据值」。
