# R003：多实体并行检索可行性调研（L2 跨公司对比）

> 日期：2026-08-17
> 状态：✅ 调研完成（结论：可行，方案见 §4）
> 背景：L2 跨公司对比 query（如"中国能建和中国铁建2025年营收谁更高？"）一次检索召回混合数据，需验证多实体隔离检索可行性

---

## 1. 问题定义

### 1.1 L2 跨公司对比场景

L2（单文档对比）共 **15 条** golden query，全部为跨公司对比模式：

| 模式 | 示例 | 数量 |
|------|------|------|
| 两公司 + 单一指标 + "谁更高/更多" | "中国能建和中国铁建2025年营收谁更高？" | 15/15 |

**核心诉求**：一次 query 需**同时**召回 2 家公司的同一指标数据，LLM 才能对比得出结论。

### 1.2 当前行为（实测）

对 15 条 L2 query 跑现有 `routeQuery`（`identifyCompany` + `executeSqlQuery`）：

```
L2-001 | 识别: 中国铁建 | 路由: sql_standard | SQL行数: 1
L2-002 | 识别: 格力电器 | 路由: sql_standard | SQL行数: 1
...（15 条全部相同模式）
```

**缺陷**：`identifyCompany` 在命中**第一个**公司后立即 `return`，第二家公司被丢弃；SQL 只查单公司 → LLM 只拿到一家公司的数据，无法对比，只能臆测或走向量检索碰运气。

**根因**（`src/server/rag/query/query-router.ts:172`）：

```typescript
// 精确匹配 stock_name_short：命中第一个即 return（单实体设计）
for (const c of allCompanies) {
  if (query.includes(c.stockNameShort)) {
    return { stockCode: c.stockCode, ... };   // ← 只返回第一个
  }
}
```

## 2. 可行性验证（实测数据）

### 2.1 公司识别侧：全量匹配成功率

将匹配逻辑改为"收集全部命中"后对 15 条 L2 query 实测：

| 验证项 | 结果 |
|--------|------|
| 能识别出 2 家公司 | **15/15（100%）** |
| 识别为空 | 0 |
| 公司对覆盖 | 中国铁建/中国能建、格力/五粮液、片仔癀/华海药业、江苏银行/东吴证券、江苏银行/中国人保、中国长城/格力、中国人保/东吴证券、华海药业/东吴证券、格力/中国能建、五粮液/片仔癀 等 |

**结论**：`stock_mapping` 表已覆盖 L2 全部公司对，**只需把"返回第一个"改为"返回全部"**，无需新增词典。

### 2.2 数据侧：第二家公司财务数据是否在库

`financial_income`（2025 年报）实测：L2 涉及的 10 家公司**全部有数据**：

```
000066 中国长城 | 000651 格力电器 | 000858 五粮液 | 600436 片仔癀
600521 华海药业 | 600919 江苏银行 | 601186 中国铁建 | 601319 中国人保
601555 东吴证券 | 601868 中国能建
（每家 report_year=2025, report_quarter=annual 均有 1 行）
```

**结论**：SQL 侧无需补数据，只需支持多 stockCode 查询。

### 2.3 同进程并行可行性

| 论证点 | 结论 |
|--------|------|
| Node.js 单线程限制 | 不影响：DB 查询 / 向量检索 / HTTP 调用均为 **I/O 型**，事件循环天然并发，`Promise.all` 即可并行 |
| 是否需要 Worker Threads | ❌ 不需要。CPU 密集部分（embedding/rerank）已部署为独立服务（embedding:8011 / reranker:8010），本地无同步计算瓶颈 |
| 隔离性 | 每家公司独立执行 SQL/向量检索，结果各自标注 `_company`，合并时互不污染——**数据级隔离**即可满足 |
| 公司数量上限 | L2 场景固定 2 家；通用化后建议上限 3 家（超过则退回向量检索） |
| 预估耗时 | 并行后 ≈ 单公司耗时（DB 毫秒级），不随公司数线性增长 |

**结论**：同进程 `Promise.all` 并行检索完全可行，无需引入多线程。

## 3. 方案设计

### 3.1 总体架构

```
用户 query（跨公司）
   │
   ▼
identifyCompanies(query) ──► [公司A, 公司B]   （新：返回全部命中）
   │
   ▼
routeQuery 多公司分支
   ├─► Promise.all：公司A 独立 SQL ──► 结果A（标注 _company=A）
   ├─► Promise.all：公司B 独立 SQL ──► 结果B（标注 _company=B）
   │
   ▼
合并结果 ──► LLM 上下文注入（两公司数据并列展示）
   │
   ▼
LLM 对比回答（"A 的营收更高，差额约 X 亿"）
```

### 3.2 代码改造点（4 处）

| # | 文件 | 改动 | 影响面 |
|---|------|------|--------|
| 1 | `src/server/rag/query/query-router.ts` | `identifyCompany` → 新增 `identifyCompanies(query): Promise<CompanyMatch[]>`（返回全部命中；原函数保留为取第一个，供单公司场景兼容） | 无破坏性 |
| 2 | 同上 `executeSqlQuery` | 新增多公司版本：`executeSqlQueryForCompanies(stockCodes: string[], indicators, ...)`，内部对每公司 `Promise.all` 调用现有单公司查询，结果标注 `_stockCode`/`_stockName` | 复用现有查询，改动小 |
| 3 | 同上 `routeQuery` | 公司数 ≥2 时走 `sql_standard_multi` 分支（合并结果 + `companies: CompanyMatch[]`）；仍只识别 1 家时走原逻辑 | 单公司路径零回归 |
| 4 | `src/server/agents/simpleAgent.ts` | `sql_standard_multi` 分支：用 `formatSqlResultAsText` 按公司分组格式化，注入两公司并列上下文 | 只加分支 |

### 3.3 注入格式（LLM 对比所需）

```text
[公司A: 中国铁建（601186）]
营业收入: 4529.30 亿元

[公司B: 中国能建（601868）]
营业收入: 10297.84 亿元

请对比上述两家公司的数据回答用户问题，说明谁更高及差额。
```

### 3.4 边界与降级

| 场景 | 处理 |
|------|------|
| 识别出 2 家但其中 1 家 SQL 无数据 | 注入有数据的公司 + 提示另一家无数据 → 走向量检索补充 |
| 识别出 ≥3 家公司 | 取前 2 家 + 向量检索补充（防御：L2 全为 2 家） |
| 非数值类跨公司 query（如"哪家研发投入大"） | 多公司向量检索并行（`Promise.all` 每公司独立 `hybridSearch`），结果合并 |
| 单公司 query | 完全走原路径（`identifyCompany` 兼容） |

## 4. 验收标准

1. **15/15 L2 query**：`identifyCompanies` 均识别出 2 家公司
2. **SQL 合并**：`routeQuery` 对 L2 query 返回 `sql_standard_multi`，`sqlResult` 包含 2 家公司数据（各标注来源公司）
3. **LLM 对比正确**：随机抽 5 条 L2 人工验证，回答均含"谁更高 + 数值 + 差额"
4. **回归**：现有 692 测试全通过；单公司 query（L1）路由行为不变
5. **耗时**：多公司并行检索延迟 ≤ 单公司延迟 × 1.5

## 5. 工作量与风险

| 项 | 评估 |
|----|------|
| 工作量 | 0.5 天（核心 3 处改动 + 1 处注入格式化） |
| 风险 | 低：单公司路径完全保留；多公司仅新增分支 |
| 数据风险 | 无：只读现有 stock_mapping / financial_* 表 |
| 依赖 | 无新依赖，纯函数 + drizzle |

---

## 6. 结论

**R003 可行，推荐方案 A（多实体识别 + 同进程 Promise.all 并行 SQL/向量检索）**：

1. 公司识别侧零成本——`stock_mapping` 已覆盖全部 L2 公司对，仅需把"返回第一个"改为"返回全部"
2. 数据侧零成本——10 家 L2 公司 2025 财务数据全部在库
3. 无需多线程——DB/向量均为 I/O 型，`Promise.all` 天然并行且数据级隔离
4. 改动收敛——4 处代码点、单公司路径零回归、0.5 天工作量

> 调研数据来源：`scripts/qa-golden.json`（130 条，L2 共 15 条）、`stock_mapping`（60 家）、`financial_income`（2025 年报 10 家）、实测 `routeQuery` 行为（2026-08-17）
