# 知识图谱数据质量提升方案

> 日期：2026-08-07
> 状态：⏳ 待审批

---

## 1. 现状分析

### 1.1 数据统计

| 指标 | 数值 |
|------|------|
| 总节点数 | 602 |
| 总关系数 | 552 |
| 节点标签 | 仅 `Entity`（无细分：Company/Location/Amount/Indicator等） |
| 关系标签 | 仅 `RELATION`（type存在属性中：生产75/下降74/增长62/持股58等） |
| 数值型实体 | ~148个（24.6%），如"-12,937,000.29"、"12.67%"、"1,711.18亿元" |
| 公司实体 | ~30个（五粮液/格力/招商银行等） |
| 产品/项目实体 | ~50个 |

### 1.2 核心问题

| 问题 | 严重度 | 影响 | 示例 |
|------|--------|------|------|
| **P1: 数值作为实体** | 🔴高 | 图谱检索返回"12.67%"作为实体，无法与查询"五粮液营收增长率"匹配 | `(营业收入, 增长, 12.67%)` → 12.67%不应是独立实体 |
| **P2: 实体无类型标签** | 🟡中 | 无法区分公司/地点/产品/指标，检索时无法按类型过滤 | `五粮液`和`12.67%`都是`Entity`标签 |
| **P3: 关系无方向语义** | 🟡中 | `(营业收入, 增长, 12.67%)` vs `(12.67%, 增长, 营业收入)` 语义不同但存储方式相同 | "增长"关系方向不明确 |
| **P4: 实体归一化缺失** | 🟡中 | "五粮液"、"宜宾五粮液股份有限公司"、"五粮液集团公司"是三个独立节点 | 同一公司的不同称呼未合并 |
| **P5: 提取Prompt关系类型过粗** | 🟢低 | 17种关系类型中"营收"/"利润"/"负债"是属性而非关系 | `(直销模式, 营收, 14,511,634,155.75元)` 应为属性 |

### 1.3 对检索的影响

当前 `graphSearch` 流程：
1. LLM提取查询实体 → 如"五粮液"、"营收"
2. Cypher路径查询 → `MATCH path = (e:Entity {name: "五粮液"})-[:RELATION*1..2]-(related) RETURN path`
3. 返回路径描述 → 如"五粮液 -[增长]-> 12.67%"

**问题**：步骤2精确匹配`name`属性，但"营收"不是实体名（实体名是"营业收入"），导致检索不到相关路径。

## 2. 改进方案

### 方案A：轻量级修复（推荐，1-2天）

**目标**：修复P1+P2，最小改动提升检索质量

#### A1: 实体类型标签化

修改 `graph-builder.ts` 的 MERGE 语句，根据实体特征自动添加类型标签：

```cypher
-- 当前
MERGE (h:Entity {name: $head})

-- 改进后
MERGE (h:Entity {name: $head})
SET h:Company    // 如果匹配公司名库
SET h:Location   // 如果匹配地名库
SET h:Product    // 如果匹配产品名
SET h:Indicator  // 如果是指标名（营业收入、净利润等）
SET h:Amount     // 如果是数值（不应作为独立实体）
```

**实现**：
- 在 `entity-extractor.ts` 中添加实体分类逻辑
- 公司名库：从PostgreSQL `companies` 表获取
- 数值检测：正则 `^[0-9\-,.%元万亿]+$`
- 指标检测：关键词列表（营业收入/净利润/ROE/毛利率等）

#### A2: 数值内联化（P1修复）

修改 `entity-extractor.ts` 的提取Prompt，将数值作为关系属性而非独立实体：

```
当前：(营业收入, 增长, 12.67%)  →  12.67%是独立节点
改进：(五粮液, 营业收入增长, 12.67%)  →  数值存在关系属性value上
```

修改 MERGE 语句：
```cypher
MERGE (h:Entity {name: $head})
MERGE (t:Entity {name: $tail})
MERGE (h)-[r:RELATION {type: $relation, sourceDocId: $docId}]->(t)
SET r.value = $value   // 数值存在关系属性上
```

#### A3: 实体归一化（P4修复）

在 `entity-extractor.ts` 中添加别名映射表：
- "五粮液" / "宜宾五粮液股份有限公司" / "五粮液集团公司" → 统一为 "五粮液"
- "格力" / "格力电器" / "珠海格力电器股份有限公司" → 统一为 "格力电器"
- 映射表从PostgreSQL `companies` 表的 `stockNameShort`/`stockNameFull` 生成

#### A4: 检索增强

修改 `graph-retriever.ts`：
- 实体匹配从精确匹配改为模糊匹配（CONTAINS/别名映射）
- 查询"营收"时同时搜索"营业收入"相关实体
- 过滤掉 Amount 类型节点的路径

### 方案B：深度重构（3-5天，需更多资源）

在方案A基础上：
- B1: 关系类型细化为有向语义关系（如 `HAS_REVENUE`/`OWNS_SHARE`/`LOCATED_IN`）
- B2: 引入本体层（Ontology），定义实体类型层次结构
- B3: 图谱嵌入（Graph Embedding），支持语义相似度检索
- B4: 增量更新机制，文档更新时只更新变更的三元组

### 方案对比

| 维度 | 方案A（轻量级） | 方案B（深度重构） |
|------|----------------|------------------|
| 工期 | 1-2天 | 3-5天 |
| 改动范围 | entity-extractor + graph-builder + graph-retriever | 全部图谱模块 + 新增本体层 |
| 检索提升 | 预计+30%（过滤噪声+归一化） | 预计+60%（语义匹配+本体推理） |
| 风险 | 低（增量修改） | 中（需重建图谱数据） |
| 是否需重建图谱 | 是（清理旧数据+重新提取） | 是 |
