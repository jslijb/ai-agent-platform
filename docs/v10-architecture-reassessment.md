# V10 RAG 评估架构重新评估报告

> **结论先行**：10 个版本迭代效果不理想的根本原因，不在于检索算法或 LLM Prompt 的微调，而在于**三个架构级缺陷**：知识库覆盖度不足（38%的query问的内容库里没有）、缺少意图识别层（对抗性问题走了普通检索）、评估指标与知识库实际不对齐（canAnswer标记错误）。继续在现有框架内微调权重和Prompt，边际收益趋近于零。

**但期望行为是**：系统应该识别出这是对抗性/违规问题，**主动拒绝并给出合规风险提示**，而不是返回"未找到"。

**这是架构级缺陷**：缺少意图识别层，所有问题不分类型都走同一条检索-生成链路。

## 三、根本性架构问题

### 问题 1：知识库覆盖度严重不足（影响 50 条，占 38%）

**测试集覆盖 10 家公司，知识库只有 5-6 家**：

| 公司 | 知识库状态 | 受影响 query 数 |
|:---|:---|:---|
| 中国能建 | ✅ 有 | 0 |
| 中国铁建 | ✅ 有 | 0 |
| 中国人保 | ✅ 有 | 0 |
| 五粮液 | ✅ 有 | 0 |
| 格力电器 | ✅ 有 | 0 |
| 中国长城 | ✅ 有 | 0 |
| 片仔癀 | ❌ 无 | ~8 |
| 华海药业 | ❌ 无 | ~6 |
| 江苏银行 | ❌ 无 | ~6 |
| 东吴证券 | ❌ 无 | ~6 |

**30%+ 的 query 问的内容知识库里根本没有**。LLM 正确回答"未找到"，但被评估系统判为"错误拒绝"给低分。这不是 LLM 的问题，也不是检索的问题，是**数据覆盖**的问题。

### 问题 2：缺少意图识别层（影响 20 条，占 15%）

当前架构：

```
用户问题 → 混合检索 → LLM生成 → 返回答案
```

**所有问题不分类型都走同一条链路**。但 L7（合规风控）和 L8（对抗性）本质上不需要检索——它们需要的是**识别问题意图后直接拒绝**。

期望架构：

```
用户问题 → 意图识别
  ├─ 事实查询 → 混合检索 → LLM生成 → 返回答案
  ├─ 投资建议/合规 → 合规拒绝模板 → 返回风险提示
  └─ 对抗性/违规 → 安全拒绝模板 → 返回违法警示
```

**L7+L8 共 20 条 query，占 15%**，全部因为缺少意图识别层而失败。

### 问题 3：评估指标与知识库不对齐（影响 ~30 条，占 23%）

qa-golden.json 中，`canAnswer=true` 表示"系统应该能回答这个问题"。但实际上：

| Query | canAnswer 标记 | 知识库有数据吗 | 评估结果 | 问题 |
|:---|:---|:---|:---|:---|
| 片仔癀2025年营业收入？ | true | ❌ 无 | answerRelevance=0.21 | canAnswer 标记错误 |
| 华海药业2025年净利润？ | true | ❌ 无 | answerRelevance=0.21 | canAnswer 标记错误 |
| 江苏银行2025年净利润？ | true | ❌ 无 | answerRelevance=0.21 | canAnswer 标记错误 |
| 东吴证券2025年营业收入？ | true | ❌ 无 | answerRelevance=0.21 | canAnswer 标记错误 |

**canAnswer=true 但知识库没有数据**，导致 LLM 的正确拒绝被误判为"错误拒绝"，answerRelevance 被压到 0.21。这直接拉低了整体 Answer Relevance 指标。

### 问题 4：检索算法对动词性查询能力弱（影响 8 条，占 6%）

L7 合规风控中 8 条失败的 query 共同特征：包含"该不该卖""长期持有""抄底""定投""加仓"等**动词性投资行为词**。

知识库中有"金融投资合规与风险提示指南"，但标题和内容中没有"抄底""定投""加仓"这些口语化词汇，导致 BM25 和向量检索都无法匹配。

**根因**：检索算法没有**查询改写/扩展**机制。用户问"该不该抄底"，系统应该改写为"投资建议 合规 风险提示"再检索。

### 问题 5：文档数据与测试集期望值不一致

| Query | 文档数据 | 期望答案 | 差异 |
|:---|:---|:---|:---|
| 中国铁建2025年营收同比增长率 | -3.50% | +3.8% | **符号相反** |
| 中国能建2025年营业收入 | 3569.66亿元 | 3865亿元 | 差295亿 |
| 中国铁建2025年营业收入 | 10297.845亿元 | 11068亿元 | 差770亿 |

**测试集的期望答案可能基于错误的数据来源**，或文档中的数据本身有误。即使 LLM 完美检索并回答，也会因为与期望答案不一致而得低分。

## 四、V1-V10 迭代效果分析：为什么 10 个版本改善缓慢

### 4.1 各版本修改内容 vs 指标变化

| 版本 | 主要修改 | AR 变化 | CR 变化 | F 变化 | 评价 |
|:---|:---|:---|:---|:---|:---|

| V3 | Prompt 调整 | -0.262↓ | -0.088↓ | +0.099 | AR 继续暴跌 |
| V4 | 评估指标修正 | +0.016 | +0.190↑ | -0.069 | CR 改善 |
| V5 | 熔断器调整 | 超时 | — | — | 失败 |

| V7 | 微调 | -0.004 | +0.001 | -0.003 | 几乎无变化 |

| V9 | 拒绝场景特殊处理 | — | — | — | — |
| V10 | 限流优化 | →0.548 | →0.652 | →0.817 | 基本停滞 |

### 4.2 为什么改善缓慢

**V1-V7 的修改集中在检索参数和 Prompt 微调**，但这些修改无法解决根本问题：
- 调整 RRF_K 参数无法让知识库里没有的文档出现
- 修改 Prompt 无法让 LLM 回答它不知道的公司数据
- 调整权重无法修复 canAnswer 标记错误

**V8 是唯一有实质改善的版本**（AR +0.118, CR +0.201, F +0.140），因为 V8 修改了评估逻辑（canAnswer 感知 + 权重调整 + Context Recall 最低 0.6），而非修改检索或生成。

**V9-V10 基本停滞**，因为能调的参数都调完了，剩下的都是架构级问题。

**结论**：V1-V7 在检索参数和 Prompt 层面微调，边际收益趋近于零。V8 在评估逻辑层面修改才有实质突破。V9-V10 再次停滞。**当前的架构优化空间已经耗尽**。

## 五、根本性改进方案

### 方案 1：补全知识库覆盖（解决 38% 的 query）

**当前缺失**：片仔癀、华海药业、江苏银行、东吴证券 4 家公司的财报数据。

**行动**：
1. 从魔塔社区或巨潮资讯网下载这 4 家公司的 2025 年年度报告 PDF
2. 使用批量上传脚本（`scripts/batch_upload_reports.py`）上传到知识库
3. 确认 PDF 解析和 Embedding 处理完成

**预期效果**：L1 最低 5 条 + L4 中 7 条 + 其他散布 query，约 25-30 条 query 的 Answer Relevance 从 ~0.21 提升到 ~0.6+

### 方案 2：增加意图识别层（解决 15% 的 query）

在 Agent 的 system prompt 中增加**意图分类规则**，在检索前先判断问题类型：

```
问题类型判断规则：
1. 对抗性问题（预测股价/操纵市场/内幕消息/保证盈利/涨停预测/老鼠仓）
   → 直接返回安全拒绝模板，不检索
2. 投资建议问题（该不该买/卖/持有/加仓/抄底/定投/推荐）
   → 检索合规规则文档 + 返回合规拒绝模板
3. 事实查询问题（营收/净利润/财务数据/规则/指标）
   → 走正常 RAG 检索流程
```

**预期效果**：L8 全部 10 条 + L7 中 8 条，共 18 条 query 从 ~0.36 提升到 ~0.8+

### 方案 3：修正测试集 canAnswer 标记（解决 23% 的评估失真）

对 qa-golden.json 中所有 canAnswer=true 的 query，逐条检查知识库是否包含相关数据：

- 知识库有数据 → canAnswer=true（保持不变）
- 知识库无数据 → canAnswer=false（修正为"正确拒绝"）

**预期效果**：约 20-25 条 query 的 answerRelevance 从 ~0.21 提升到 1.0（正确拒绝）

### 方案 4：增加查询改写/扩展（解决 6% 的 query）

在检索前增加查询改写步骤：

```
原始查询："五粮液现在是不是该卖了？"
改写后查询1："五粮液 投资建议 卖出 合规"
改写后查询2："投资建议 风险提示 合规规则"
```

使用 LLM 或规则映射，将口语化投资行为词扩展为合规关键词。

**预期效果**：L7 中 8 条检索失败的 query，部分能匹配到合规文档

### 方案 5：修正测试集期望值（解决数据不一致）

逐条核对测试集中有数据的公司的期望答案与知识库文档中的实际数据：

## 七、V1-V10 失败的深层教训

### 教训 1：在错误的方向上努力 10 个版本

V1-V7 集中在检索参数微调和 Prompt 调整，但这些修改无法解决数据覆盖和架构缺陷问题。**应该在 V2 就做 query 级失败分析**，而不是等到 V8 才开始。

### 教训 2：评估指标失真掩盖了真实问题

canAnswer 标记与知识库实际不对齐，导致 LLM 的正确拒绝被判为错误拒绝，answerRelevance 被人为压低。**这个评估失真让团队误以为"答案质量差"**，实际上 30% 的低分是因为知识库没有数据而非 LLM 能力不足。

### 教训 3：缺少分层诊断

10 个版本迭代中，没有系统地做"检索层→生成层→评估层"的分层诊断。每次都是看总体指标 → 调参数 → 再跑评估。**正确的做法是**：先逐条 query 分析失败在哪一层，再针对性修复。

### 教训 4：架构设计缺少意图识别

所有问题都走同一条 RAG 链路，没有区分问题类型。L7+L8 共 20 条 query（15%）本不需要检索，但因为走了检索流程而全部失败。**意图识别应该是 RAG 系统的第一层**，不是事后补丁。
