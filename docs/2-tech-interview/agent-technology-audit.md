## 二、逐项详解 + 为何适用于本项目

### 1. ReAct 循环（Reasoning + Acting）

**代码位置**：`simpleAgent.ts:1060-1733`（`runAgent` 主循环）

**实现**：`for (let i = 0; i < maxIterations; i++)` 中每轮：
1. 调 LLM → 获取 thought 或 tool_call
2. 执行工具 → 得到 observation
3. 推入 messages → 继续下一轮

支持原生 function calling（bailian/agnes 的 `tool_calls` 字段）和文本 JSON 解析两种模式。

**为何适用本项目**：金融分析天然需要多步推理——先获取行情数据，再计算技术指标，最后综合分析。单次 LLM 调用无法完成，必须通过 ReAct 循环让 Agent 自主决定调用哪些工具、按什么顺序。

**面试话术**：*"我们的 Agent 采用 ReAct 范式，最多迭代 5 轮。每轮 LLM 自主决定是调用工具还是直接回答。金融场景下，Agent 需要先获取行情、再算指标、最后综合分析，单次调用无法完成，ReAct 循环是必需的。"*

---

### 2. 工具调用（Function Calling）

**代码位置**：
- 工具定义：`simpleAgent.ts:301-374`（6个合并工具）
- 工具注册：`tools/registry.ts`（`ToolRegistryClass`）
- 参数校验：`simpleAgent.ts:1464-1583`
- 文本解析：`simpleAgent.ts:416-543`（6种格式兼容）

**实现**：6 个合并工具（technicalAnalysis/riskAnalysis/complianceCheck/marketData/toolSearch/hybridSearch），每个工具有 JSON Schema 参数定义。支持原生 function calling 和文本 JSON 解析双模式。调用前通过 `ToolCallValidator` 校验参数类型和必填项。

**为何适用本项目**：金融分析需要大量专业计算（MA/MACD/RSI/VaR/Sharpe等），这些计算必须由工具精确执行，不能让 LLM "猜"。合并工具自动获取数据（fetchStockData），避免 LLM 需要先调 marketData 再调计算工具的两步操作。

**面试话术**：*"我们把 21 个细粒度工具合并为 6 个合并工具，减少 system prompt 的 token 消耗约 60%。每个合并工具自动获取数据，LLM 只需一次调用即可完成'取数据+计算'。同时兼容原生 function calling 和文本 JSON 解析，确保不同 LLM provider 都能正确调用。"*

---

### 3. 反思/自我修正（Reflection/Self-Correction）

**代码位置**：
- `reflection-node.ts:10-112`（`shouldRetrieveAgain`）
- `simpleAgent.ts:1211-1329`（反思评估阶段）

**实现**：当 LLM 给出答案但未调用工具时，调用另一个 LLM 评估答案是否充分、是否存在幻觉。如果 `needMore=true`，根据建议补充检索或注入工具调用指令。反思最多 3 轮。System Prompt 中特别强调"幻觉检测规则"。

**为何适用本项目**：金融数据容不得幻觉——编造的股价、错误的指标计算会导致严重后果。反思机制是防止 Agent 在没有数据支撑时"瞎编"的关键防线。

**面试话术**：*"金融场景对幻觉零容忍。我们的反思机制在 Agent 给出答案后，用另一个 LLM 评估答案是否有数据支撑。如果检测到幻觉风险，会强制补充检索或重新调用工具。这比单纯依赖 prompt 约束更可靠。"*

---

### 4. 记忆系统（4层架构）

**代码位置**：`memory.ts` 全文（799行）

**架构**：
| 层级 | 内容 | Token预算 | 存储 |
|------|------|----------|------|
| L1 | 最近对话（10条） | 30% | PostgreSQL messages 表 |
| L2 | 滚动摘要 | 25% | memorySummaries 表 |
| L3 | 历史片段（关键数据点） | 25% | memoryFragments 表 |
| L4 | 用户画像（偏好/风险/投资风格） | 10% | memoryProfiles 表 |

**关键实现**：
- Token 预算动态分配：`calculateTokenBudget`（`memory.ts:398-411`）
- L2 摘要：每 6 条消息触发 LLM 异步生成（`memory.ts:535-623`）
- L3 片段：从摘要中提取金融数值（股价/PE/营收等）
- L4 画像：正则匹配用户偏好表达（`memory.ts:344-387`）
- 三级作用域：personal/team/enterprise（`memory.ts:665-799`）

**为何适用本项目**：金融对话往往跨越多个会话（"上次讨论的茅台分析"），需要长期记忆。4层架构平衡了信息完整性和 token 预算——L1 保证近期上下文，L2/L3 压缩历史信息，L4 记住用户偏好（如"偏好价值投资"）。

**面试话术**：*"我们实现了 4 层记忆架构，灵感来自 MemGPT。L1 是最近 10 条消息，L2 是 LLM 生成的滚动摘要，L3 是从摘要中提取的金融关键数据点，L4 是用户画像。每层有 token 预算，总预算 6000 token。金融场景下，用户经常引用之前的分析，4 层记忆确保跨会话信息不丢失。"*

### 5. RAG 检索增强

**代码位置**：
- 混合检索：`hybrid-retriever.ts:29-128`（稠密+稀疏 RRF 融合）
- 稠密检索：`dense-retriever.ts:152-220`（pgvector 余弦相似度）
- 稀疏检索：`sparse-retriever.ts:203-250`（BM25）
- 重排序：`reranker.ts:11-73`（bge-reranker API）
- 查询扩展：`query-expander.ts`（金融同义词）
- 语义切分：`semantic-chunker.ts`（标题+段落+表格行）

**实现**：两阶段 RAG 管线——粗排（稠密 pgvector + 稀疏 BM25 → RRF 融合）→ 精排（bge-reranker API）。粗排取 topK×2，精排取 topK。精排失败时降级为粗排结果截取。文档上传后自动切片→嵌入→存入 pgvector。

**为何适用本项目**：金融分析需要引用研报、公告等文档。纯稠密检索对关键词（股票代码"600519"）不敏感，纯稀疏检索对语义（"白酒龙头"→茅台）不敏感。混合检索+重排序是金融 RAG 的最佳实践。

**面试话术**：*"RAG 采用两阶段管线：粗排用稠密 pgvector + 稀疏 BM25 的 RRF 融合，精排用 bge-reranker。金融场景下，用户可能说'白酒龙头'（语义）也可能说'600519'（关键词），混合检索两种都能命中。精排失败时自动降级为粗排截取，保证可用性。"*

---

### 6. 多步推理（Chain of Thought）

**代码位置**：`simpleAgent.ts:1060-1733` + System Prompt 19条规则（`simpleAgent.ts:854-977`）

**实现**：Agent 主循环最多 5 轮迭代，每轮 LLM 可以推理+调用工具+观察结果。System Prompt 详细规定了 CoT 引导规则："何时必须调用工具"、"立即回答原则"、"禁止重复调用"等。

**为何适用本项目**：金融分析本质是多步推理——获取数据→计算指标→综合分析→给出结论。System Prompt 的规则确保 LLM 遵循正确的推理路径，而不是跳过中间步骤直接"猜"结论。

---

### 7. 错误恢复（Checkpoint + Resume）

**代码位置**：
- `checkpoint.ts` 全文（Redis 存储）
- `simpleAgent.ts:1676-1732`（catch 块中恢复逻辑）

**实现**：三层错误恢复：
1. **Checkpoint+Resume**：每轮工具调用后保存进度到 Redis（TTL=3600s），错误时从 checkpoint 恢复上下文继续，最多重试 2 次
2. **LLM 降级链**：模型 A 失败自动切换模型 B/C（`router.ts:88-145`）
3. **工具验证重试**：参数校验失败时让 LLM 修正参数最多 3 次（`enhanced-react-executor.ts:131-163`）

**为何适用本项目**：金融 API 调用可能因网络/限流/数据源故障失败。Checkpoint 确保已完成的工具调用不丢失，降级链确保 LLM 服务中断时有备选方案。

**面试话术**：*"我们实现了三层错误恢复：Checkpoint 保存每轮进度到 Redis，失败后从断点恢复；LLM 降级链在模型 A 失败时自动切换模型 B/C；工具参数校验失败时让 LLM 修正参数。金融 API 不稳定，这些机制确保 Agent 不会因单点故障而完全失败。"*

---

### 8. 上下文压缩（Context Compaction）

**代码位置**：`context-compaction.ts` 全文（180行）

**实现**：对话消息 >20 条时触发压缩。保留最近 5 条，对早期消息调用 LLM 生成结构化摘要（保留 decisions/toolResults/userPrefs/financialData）。金融数值保留原始精度。LLM 摘要失败时降级为正则提取金融数值。

**为何适用本项目**：金融对话容易很长（反复查询不同指标），但 LLM 上下文窗口有限。压缩时特别保留金融数值的原始精度，避免"茅台PE=30"被压缩成"茅台估值较高"丢失关键信息。

**面试话术**：*"上下文压缩对金融数据有特殊处理——金融数值保留原始精度，不会被四舍五入或模糊化。压缩失败时降级为正则提取，确保关键数据不丢失。"*

---

### 9. 工具合并/按需加载

**代码位置**：
- 6个合并工具：`simpleAgent.ts:301-374`
- RouterFacade：`simpleAgent.ts:1024-1057`
- 向量工具检索：`tool-vector-retriever.ts`

**实现**：原 21 个工具合并为 6 个，减少 system prompt token 消耗约 60%。合并工具自动获取数据（fetchStockData），LLM 一次调用即可完成"取数据+计算"。RouterFacade 根据意图路由到 skill/group 时只加载相关工具子集。

**为何适用本项目**：21 个工具的 JSON Schema 定义约 4000 token，合并后约 1600 token。每次 LLM 调用都包含工具定义，减少 token = 降低成本+降低幻觉风险（工具太多 LLM 容易选错）。

---

### 10. 流式输出（SSE）

**代码位置**：`api/agent/stream/route.ts` 全文（113行）

**实现**：`ReadableStream` + SSE 协议，Agent 每执行一步就通过 `onStep` 回调推送 `step` 事件，最终推送 `done` 事件。前端 StepCard 实时展示 Agent 推理过程。

**为何适用本项目**：金融分析可能需要 10-30 秒，用户不能盯着空白页面。流式输出让用户实时看到 Agent 在做什么（"正在获取行情数据"→"正在计算MACD"→"正在分析"），提升体验。

### 11. Prompt Engineering

**代码位置**：`simpleAgent.ts:854-977`（19条核心规则）

**关键规则**：
1. 严禁编造数据（必须调用工具获取）
2. 股票代码格式（6位+交易所前缀）
3. 技术指标计算流程（先取数据→再计算→最后分析）
4. 数据来源说明（必须标注数据来源和时间）
5. 立即回答原则（有足够信息时立即回答，不要多余调用）
6. 禁止重复调用（同一工具同一参数不调两次）

**为何适用本项目**：金融 Agent 的行为约束比通用 Agent 严格得多——不能编造股价、不能给出投资建议、必须标注数据来源。19 条规则是针对金融场景的专门设计。

### 12. 安全/合规护栏（Guardrails）

**代码位置**：
- 意图识别：`simpleAgent.ts:58-153`（Unsafe/Controversial/Factual 三级）
- 合规拒绝：`simpleAgent.ts:158-259`
- 合规日志：`compliance/log.ts`

**实现**：Agent 主循环之前，先通过关键词+正则识别意图：
- **Unsafe**（预测股价/操纵市场等）→ 直接拒绝 + 引用《证券法》
- **Controversial**（投资建议类）→ 检索财务数据 + 合规拒绝 + 数据参考
- **Factual**（事实查询）→ 正常处理

所有拦截记录写入 compliance_logs 表（保存 5 年），同一用户 24h 内 3 次 Unsafe 触发人工审核。

**为何适用本项目**：金融 AI 必须遵守《证券法》《基金法》等法规。提供投资建议是持牌业务，AI 不能越界。合规护栏是法律刚需，不是可选功能。

**面试话术**：*"合规护栏是金融 AI 的法律刚需。我们把用户意图分为三级：Unsafe 直接拒绝并引用《证券法》，Controversial 提供数据参考但明确拒绝投资建议，Factual 正常处理。所有拦截记录保存 5 年，24h 内 3 次 Unsafe 触发人工审核。"*

### 13. 多模型支持 + 降级链

**代码位置**：`router.ts` 全文 + `bailian.ts` + `agnes.ts`

**实现**：从 `config/api_keys.yaml` 读取模型降级链。支持 2 个 provider（dashscope/bailian + agnes）。调用时按链顺序逐一尝试，失败自动降级。额度耗尽(304/403)时强制打开熔断器跳过该模型。

**为何适用本项目**：LLM 服务不稳定（限流/宕机/额度耗尽），金融分析不能因单模型故障而中断。降级链确保总有可用的模型。

---

### 14. 限流/熔断

**代码位置**：`rate-limiter.ts` + `circuit-breaker.ts`

**实现**：
- 限流器：Redis INCR+EXPIRE 滑动窗口（20请求/60秒），降级为内存 Map
- 熔断器：Redis HSET 存储状态，closed→open(30s)→half-open 三态。每个 LLM 模型独立熔断器

**为何适用本项目**：LLM API 有调用频率限制和成本考量。限流防止恶意刷接口，熔断防止故障模型持续拖慢响应。

---

### 15. LLM 缓存（⚠️ 名称有误导）

**代码位置**：`cache.ts` 全文（97行）

**实现**：双层缓存（Redis 优先 + 内存降级），仅缓存 temperature=0 的请求。缓存键由 messages 内容 hash 生成。**这是精确匹配缓存，不是语义缓存**——相同 messages 命中，语义相似但表述不同不会命中。

**为何适用本项目**：减少重复 LLM 调用成本。但精确匹配缓存在 Agent 场景下命中率较低（每轮 messages 都不同），实际价值有限。

**面试注意**：如果面试官问"语义缓存"，需要诚实说明当前实现是精确匹配缓存，语义缓存需要额外引入 embedding 相似度比较。

---

### 16. Agent 日志/可观测性

**代码位置**：`agent-logger.ts` + `simpleAgent.ts:284-291`（AgentStep 接口）

**实现**：6 种步骤类型（thinking/tool_call/tool_result/reflection/retrieval/answer），每步记录耗时（毫秒级）。写入 agent_logs 表，前端 StepCard 展示。

**为何适用本项目**：金融分析的可解释性要求高——用户需要知道 Agent 用了什么数据、算了什么指标、花了多长时间。可观测性是合规和信任的基础。

---

### 17. 知识图谱（Neo4j）— ⚠️ 堆技术

**代码位置**：`graph/neo4j.ts` + `graph/graphrag.ts` + `graph/builder.ts` — **全是空壳（`export {}`）**

**判断**：**典型的堆技术**。docker-compose 中部署了 neo4j 容器，但 Agent 主流程完全不依赖图谱功能。3 个源文件都是空壳。

**面试建议**：不要主动提及知识图谱。如果被问到，诚实说明"预留了接口但未实现，因为当前 RAG 混合检索已满足需求，图谱的实体关系查询场景（如公司关联交易分析）是后续规划"。

---

### 18. 评估系统

**代码位置**：`evaluation/` 目录

**实现**：
- RAG 评估：4 维度（Faithfulness/AnswerRelevance/ContextRecall/ContextPrecision）
- Agent 评估：5 维度（工具选择/规划/合规/一致性/效率）
- 评估触发：手动 + 自动（定时/部署后/文档更新/错误率上升）
- 开放数据集适配器：CFLUE/FinEval
- 当前基线：V13-r6 综合 0.9153

**为何适用本项目**：金融 AI 的准确性至关重要，必须有量化评估。评估系统确保每次代码变更不会导致质量退化。

## 四、面试高频问题 + 本项目回答模板

### Q1: "你的 Agent 用了什么架构？"
> ReAct 范式，最多 5 轮迭代。每轮 LLM 自主决定调用工具还是直接回答。金融分析需要多步推理（取数据→算指标→综合分析），ReAct 是自然选择。

### Q2: "如何防止幻觉？"
> 三层防线：(1) System Prompt 19 条规则明确禁止编造数据；(2) 反思机制——答案给出后用另一个 LLM 评估是否有数据支撑；(3) 合规护栏——意图识别在前端拦截高风险查询。

### Q3: "记忆系统怎么设计的？"
> 4 层架构（L1 对话/L2 摘要/L3 片段/L4 画像），灵感来自 MemGPT。每层有 token 预算，总预算 6000 token。金融数值在压缩时保留原始精度。

### Q4: "RAG 怎么做的？"
> 两阶段管线：粗排（稠密 pgvector + 稀疏 BM25 → RRF 融合）→ 精排（bge-reranker）。金融场景下用户可能说"白酒龙头"也可能说"600519"，混合检索两种都能命中。

### Q5: "工具为什么合并？"
> 21→6 个工具，system prompt token 减少 60%。工具越多 LLM 越容易选错（选择困难），合并后每个工具功能内聚，LLM 选择更准确。合并工具自动获取数据，减少调用轮次。

### Q6: "错误怎么处理？"
> 三层恢复：Checkpoint 保存进度到 Redis，失败后从断点恢复；LLM 降级链在模型 A 故障时切换 B/C；工具参数校验失败时让 LLM 修正参数最多 3 次。

### Q7: "合规怎么保证？"
> 三级意图分类：Unsafe 直接拒绝+引用《证券法》，Controversial 提供数据参考但拒绝投资建议，Factual 正常处理。拦截记录保存 5 年，24h 内 3 次 Unsafe 触发人工审核。

### Q8: "上下文窗口不够怎么办？"
> 上下文压缩：>20 条消息时，保留最近 5 条，早期消息由 LLM 生成结构化摘要。金融数值保留原始精度。压缩失败时降级为正则提取。

### Q9: "有没有堆技术？"
> 知识图谱（Neo4j）是空壳，预留了接口但未实现。因为当前 RAG 混合检索已满足需求，图谱的实体关系查询场景（如公司关联交易分析）是后续规划。LLM 缓存是精确匹配缓存，不是语义缓存，命中率有限。

### Q10: "评估怎么做的？"
> RAG 4 维度（Faithfulness/AR/CR/CP）+ Agent 5 维度（工具选择/规划/合规/一致性/效率），支持 LLM 评估+启发式降级。当前基线 V13-r6 综合 0.9153。每次代码变更跑回归测试确保不退化。

## 五、技术适用性总结

本项目是**金融分析 Agent**，技术选型的核心原则：

| 原则 | 体现 |
|------|------|
| **准确性 > 速度** | 反思机制、合规护栏、工具强制调用 |
| **可解释性** | 6种步骤类型、耗时追踪、数据来源标注 |
| **容错性** | 三层错误恢复、降级链、熔断器 |
| **合规性** | 三级意图分类、拦截日志保存5年 |
| **成本控制** | 工具合并减token、缓存、限流 |
| **不堆技术** | 知识图谱预留未实现，LLM缓存诚实标注为精确匹配 |
