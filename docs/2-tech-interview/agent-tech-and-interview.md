## 零、项目开场白（面试1分钟版本）

### 这是什么项目？

一个**金融AI Agent平台**——用户用自然语言提问（比如"招商银行2025年营业收入多少？""帮我算MA20和RSI14""买入100股招商银行合规吗？"），AI自动理解意图、调用工具、检索财报、计算指标、检查合规，给出带数据溯源的回答。

### 核心价值是什么？

把金融分析师的**3种工作**自动化：
1. **查数据**：从200页PDF财报中精准找到"营业收入832亿元"——RAG混合检索+知识图谱
2. **算指标**：MA/RSI/MACD/波动率/VaR等20+技术/风险指标——Function Calling工具链
3. **查合规**：涨跌幅限制、持仓上限、受限股票检查——合规护栏+规则引擎

### 技术栈一句话

**前端**：Next.js + SSE流式输出 + NextAuth认证
**后端**：FastAPI(Python) + Node.js Agent(ReAct循环)
**数据**：PostgreSQL(pgvector) + Neo4j + Redis
**AI**：阿里百炼/Agnes + Function Calling + 知识图谱 + 语义缓存
**运维**：Docker 5容器 + nginx + CI/CD

### 用什么评估的？

基于**RAGAS思想自实现**的RAG评估框架，4个核心指标：

| 指标 | 全称 | 通俗解释 | 达标线 |
|------|------|---------|--------|
| **CP** | Context Precision | 检索回来的10条内容，相关的排前面了吗？ | ≥0.80 |
| **CR** | Context Recall | 标准答案需要的信息，检索回来了多少？ | ≥0.80 |
| **F** | Faithfulness | AI的回答有没有编造？是不是只基于检索内容？ | ≥0.85 |
| **AR** | Answer Relevancy | 回答跟问题相关吗？有没有答非所问？ | ≥0.80 |

**评估流程**：130条金融问题（9大分类）→ Agent执行 → 收集检索context+回答 → LLM评判4指标 → 加权平均

**为什么自实现不用官方库？** 官方RAGAS库要求用OpenAI embedding，但项目用bge-m3本地embedding，接口不兼容。自实现用bge-m3算向量相似度，用阿里百炼/Agnes做LLM评判，与生产环境一致。

**迭代历程**：V12(0.57) → V13(0.78) → V13-r4(0.87首次达标) → V13-r6(0.92)，核心优化是SQL结果自然语言格式化（让LLM能读懂检索回来的数据）。

## 二、技术决策对比（面试高频考点）

### 2.1 工具合并(6个) vs 多级Skill路由 — 详细对比

**背景**：最初有21个细粒度工具（MA/RSI/MACD/KDJ/BB/VWAP/Sharpe/MaxDD/VaR/Corr/历史行情/实时行情/财务数据/财报/合规检查/混合检索/工具搜索……），需要决定如何组织这些工具给LLM使用。

#### 方案A：多级Skill路由（LangGraph式）

```
用户Query → 意图识别 → 路由到Skill
  ├── 技术分析Skill → 加载5个技术指标工具(MA/RSI/MACD/KDJ/BB)
  ├── 风险分析Skill → 加载6个风险工具(VWAP/Sharpe/MaxDD/VaR/Corr/Vol)
  ├── 数据获取Skill → 加载4个数据工具(历史/实时/财务/财报)
  ├── 合规Skill → 加载合规工具
  └── RAG Skill → 加载检索工具
```

**优点**：
- 每次LLM调用只看到5-6个工具，token消耗低
- 工具职责清晰，LLM选择准确率高
- 扩展新工具只需加到对应Skill，不影响其他Skill

**缺点**：
- **意图识别是单点故障**：如果路由错误（如把"五粮液ROE"路由到技术分析Skill而非数据获取Skill），整个流程失败
- **跨Skill需求处理复杂**："五粮液营收和技术指标对比"需要同时用数据获取+技术分析，多Skill协作增加复杂度
- **增加一轮LLM调用**：先调意图识别LLM，再调执行LLM，延迟+成本翻倍
- **Skill间状态共享困难**：不同Skill的上下文如何传递？
- **调试困难**：出错时需要追踪"是路由错了还是工具错了"

#### 方案B：6个合并工具（我们的选择）

```
用户Query → LLM直接从6个工具中选择
  ├── technicalAnalysis → 内部自动获取数据+计算MA/RSI/MACD/KDJ/BB
  ├── riskAnalysis → 内部自动获取数据+计算VWAP/Sharpe/MaxDD/VaR/Corr/Vol
  ├── marketData → 统一数据入口(历史/实时/财务/财报)
  ├── complianceCheck → 合规审查
  ├── toolSearch → 元工具，按需加载工具详情
  └── hybridSearch → RAG混合检索
```

**优点**：
- **消除意图识别单点故障**：LLM直接选工具，不需要额外路由层
- **合并工具自动获取数据**：LLM说"算MACD"，technicalAnalysis内部自动fetchStockData，不需要LLM先调marketData再调technicalAnalysis
- **跨工具需求自然处理**：LLM可以在一轮中同时调用technicalAnalysis和marketData
- **token消耗减少60%**：21个工具的JSON Schema约4000 token → 6个约1600 token
- **调试简单**：只有一层决策，出错直接看LLM选了哪个工具

**缺点**：
- 合并工具内部逻辑复杂（需要自动获取数据+参数分发）
- 工具描述需要精心设计，让LLM理解合并工具的边界
- 6个工具仍然比3个多，LLM偶尔选错

#### 量化对比

| 维度 | 多级Skill路由 | 6个合并工具 |
|------|:----------:|:---------:|
| System Prompt Token | ~800（只加载当前Skill的工具） | ~1600（6个工具定义） |
| 总LLM调用次数 | 2-3次/Query（意图识别+执行+可能跨Skill） | 1-2次/Query（直接执行） |
| 意图识别错误影响 | **致命**（整个流程走错方向） | 无（没有意图识别层） |
| 跨工具协作 | 复杂（Skill间状态传递） | 简单（同一轮可调多个工具） |
| 扩展性 | 加工具到Skill，不影响其他 | 需要修改合并工具内部 |
| 调试难度 | 高（两层决策） | 低（一层决策） |
| 工具选择准确率 | ~95%（少量工具易选） | ~90%（6个工具偶尔选错） |
| 端到端延迟 | +3-5s（额外意图识别调用） | 基准 |

#### 结论

**金融场景选合并工具更优**，原因：
1. 金融查询经常跨领域（"五粮液营收+技术面"），多级Skill路由处理跨域需求天然困难
2. 意图识别错误在金融场景代价极高——把"ROE查询"路由到技术分析Skill会导致完全无用的结果
3. 合并工具的"自动获取数据"设计消除了LLM需要先调数据工具再调计算工具的两步操作，这是最大的效率提升

**如果场景是单领域、意图明确的**（如客服只有"查订单/退款/投诉"3个意图），多级Skill路由更简洁。

#### 6个工具如何让LLM选对？传参为什么不难？

**选工具的问题**：21个工具时，LLM要在"calculateMA/calculateRSI/calculateMACD/calculateBollinger/calculateKDJ/getStockHistory/getStockRealtime/…"里选，名字太多太像，经常选错。6个工具时，LLM只需在"technicalAnalysis/riskAnalysis/marketData/complianceCheck/toolSearch/hybridSearch"里选，名字差异大，选错率大幅下降。

**传参的问题**：21个工具时，LLM要传底层参数——比如算MA，需要先调`getStockHistory`拿到价格数组`[35.2, 35.8, 36.1, ...]`，再把整个数组传给`calculateMA(data=[35.2, 35.8, ...], period=20)`。LLM传一个200个数字的数组？基本不可能成功。

**6个工具的"高层语义"设计**——LLM不需要传底层数据，只需要说"算什么"：

| 工具 | LLM只需要传 | 工具内部自动做 |
|------|-----------|-------------|
| `technicalAnalysis` | `indicator="MA", code="sh.600036", period=20` | 自动fetch历史数据→计算MA→返回结果 |
| `riskAnalysis` | `metric="MaxDrawdown", code="sh.600036"` | 自动fetch历史数据→计算最大回撤→返回结果 |
| `marketData` | `dataType="history", code="sh.600036"` | 调data-service→返回K线+缓存供后续工具用 |
| `complianceCheck` | `checkType="trade", code="sh.600036", price=35.5` | 检查涨跌幅限制→返回合规结果 |

**关键设计：数据缓存链**

```
用户问："招商银行的MA20和RSI14"
  ↓
第1轮：LLM调 marketData(dataType="history", code="sh.600036")
       → 拿到365天K线，自动缓存到内存
  ↓
第2轮：LLM调 technicalAnalysis(indicator="MA", period=20)
       → 发现缓存有数据，直接用，不用再传
       → LLM调 technicalAnalysis(indicator="RSI", period=14)
       → 同样用缓存数据
```

LLM全程不需要传价格数组，不需要知道数据从哪来，只需要说"我要算什么指标、哪只股票"——这就是"高层语义"：**把"怎么做"封装在工具内部，LLM只表达"做什么"**。

**面试追问准备**

**Q: 6个工具会不会因为参数太多，LLM传错参数？**
> 不会。每个合并工具只有1个必填参数（indicator/metric/dataType/checkType）+ 1个股票代码（code），其他参数都有默认值。比如RSI默认period=14，MACD默认fast=12/slow=26/signal=9，LLM不传也能算。21个工具时每个工具的参数更少但工具数多，选错工具的概率远大于传错参数的概率。

**Q: 如果LLM选错工具怎么办？**
> 反思节点会检测。比如用户问"波动率"，LLM错误地调了technicalAnalysis，反思节点发现technicalAnalysis不支持Volatility指标，会提示LLM改用riskAnalysis。这是6个工具+反思节点的双重保障。

### 2.2 RAG：混合检索 vs 纯稠密检索

| 维度 | 纯稠密(pgvector) | 混合检索(pgvector+BM25→RRF→reranker) |
|------|:---------:|:---------:|
| 语义查询("白酒龙头") | ✅ | ✅ |
| 关键词查询("600519") | ❌ | ✅ |
| 混合查询("五粮液ROE") | ⚠️ | ✅ |
| 延迟 | ~50ms | ~200ms（+reranker） |
| 成本 | 低 | 中（reranker API） |
| 金融场景适配 | 差 | **优** |

**结论**：金融场景必须混合检索。用户可能说"白酒龙头"也可能说"600519"，纯稠密对关键词不敏感。

## 三、面试高频问答

### Q1: "你的Agent用了什么架构？"
> ReAct范式，最多5轮迭代。每轮LLM自主决定调用工具还是直接回答。金融分析需要多步推理（取数据→算指标→综合分析），单次调用无法完成。6个合并工具让LLM一次调用完成"取数据+计算"，减少迭代轮次。

### Q2: "如何防止幻觉？"
> 三层防线：(1) System Prompt 19条规则禁止编造数据；(2) 反思机制——答案给出后用另一个LLM评估是否有数据支撑，检测到幻觉则强制补充检索；(3) 合规护栏——Unsafe意图直接拒绝引用《证券法》。实测Faithfulness=1.0满分。

### Q3: "工具为什么合并？21→6的具体理由？"
> 三个原因：(1) token减少60%（4000→1600），每次LLM调用都包含工具定义，减少token=降成本+降幻觉风险；(2) 合并工具自动获取数据，LLM只需一次调用完成"取数据+计算"，不需要先调marketData再调technicalAnalysis；(3) 工具越少LLM选择越准确，21个工具时选择困难症明显。对比多级Skill路由方案，合并工具消除了意图识别单点故障，跨工具需求自然处理。

### Q4: "RAG怎么做的？"
> 两阶段管线：粗排（pgvector+BM25→RRF融合）→精排（bge-reranker）。金融场景用户可能说"白酒龙头"也可能说"600519"，混合检索两种都命中。精排失败自动降级为粗排截取。还有查询路由层——意图识别后直接SQL查询，命中率90.9%，跳过LLM猜测。

### Q5: "知识图谱做了什么？"
> V2增强版：实体分类（Company/Indicator/Amount/Product/Location）、数值内联（"832亿元"不再作为独立节点，而是关系的value属性）、实体归一化（5534家公司别名自动合并）、12种语义关系（HAS_REVENUE/OWNS_SHARE等）。补全向量检索的盲区——实体间的隐含关系链路。

### Q6: "语义缓存怎么做的？命中率多少？"
> 分层设计：第一层Redis精确匹配（毫秒级），第二层pgvector语义匹配（embedding相似度≥0.95）。按promptTemplate分组隔离避免误匹配。实测：相同文档第二次提取三元组，耗时从69.3s降到0.0s。反思节点和图谱提取场景预估命中率20-40%。

### Q7: "记忆系统怎么设计的？"
> 4层架构（L1对话/L2摘要/L3片段/L4画像），灵感来自MemGPT。每层有token预算，总预算6000。金融数值在压缩时保留原始精度，不会被模糊化。L4用户画像记住偏好（如"偏好价值投资"），跨会话持续生效。

### Q8: "错误怎么处理？"
> 三层恢复：(1) Checkpoint保存每轮进度到Redis，失败后从断点恢复，最多重试2次；(2) LLM降级链6个模型自动切换（agnes→qwen-plus→qwen-flash→...）；(3) 工具参数校验失败时让LLM修正参数最多3次。金融API不稳定，这些机制确保Agent不会因单点故障完全失败。

### Q9: "合规怎么保证？"
> 三级意图分类：Unsafe直接拒绝+引用《证券法》，Controversial提供数据参考但拒绝投资建议，Factual正常处理。拦截记录保存5年，24h内3次Unsafe触发人工审核。这是金融AI的法律刚需。

### Q10: "评估怎么做的？准确率多少？"
> 4维度（CP/CR/F/AR）+9类130条golden dataset，7轮迭代从0.5679提升到0.9153。关键优化：SQL结果自然语言格式化器让L4 CR从0.25提升到0.60（+140%）。每次代码变更跑回归测试确保不退化。

### Q11: "有没有堆技术？"
> 早期知识图谱是空壳，现已实现V2增强版。早期LLM缓存是精确匹配（命中率~0%），现已实现语义缓存。所有技术点都有实际运行和量化数据支撑，没有"只部署不使用"的技术。

### Q12: "多Agent怎么理解？你做过吗？"
> 两种模式都做过：(1) 自媒体项目的DAG调度器——6个Agent按确定性流程编排，这是"工作流式多Agent"；(2) 金融项目的ReAct循环——单Agent动态决定调用哪些工具，这是"自主式单Agent"。如果要做"协作式多Agent"（Planner→Researcher→Critic），RouterFacade架构已预留扩展点，核心挑战是Agent间通信和共享记忆，我会用消息队列+共享Redis状态来实现。

### Q13: "自动化工作流怎么设计？"
> 两种范式：(1) 确定性工作流（DAG调度器）——适合流程固定的场景，节点按DAG拓扑执行，失败重试+跳过+告警；(2) 动态工作流（ReAct Agent）——适合流程不确定的场景，LLM每轮自主决定下一步。实际业务往往需要混合——外层DAG控制大流程，内层Agent处理不确定步骤。

### Q14: "怎么控制LLM成本？"
> 四个层面：(1) 工具合并减少token 60%；(2) 语义缓存，相同输入0.0s返回；(3) 查询路由，SQL直查跳过LLM；(4) 降级链，优先用便宜的flash模型，贵模型只在必要时使用。

## 六、文档切片策略

### 6.1 多层混合切片（已实现）

#### 问题是什么？

一份财报PDF有200页，转成文本后几十万字符。但LLM的检索窗口有限——embedding模型最多吃8192个token，检索时每个chunk必须是小块（几百字）。所以必须把长文档"切"成小块。

**核心矛盾**：切得太粗，检索不精准（一个chunk里塞了太多无关内容）；切得太细，语义断裂（一句话被切成两半，前半句说"营业收入"，后半句的数字832亿元跑到下一个chunk里去了）。

#### 解决方案：6层递进切分

想象你在切一块千层蛋糕——不是一刀切到底，而是沿着每一层的自然纹理分开：

**第1层：按标题分节** —— 一份财报天然有"一、公司简介""二、财务数据""三、风险提示"等章节，先按标题把整份文档拆成若干"节"。这就像按蛋糕的层先分开，保证每一块都是同一个主题。

**第2层：按段落合并** —— 一个章节可能有好几段，如果整节不超过800字就直接保留；如果超过800字，就按段落边界拆分，相邻小段落合并到800字为止。这就像一层蛋糕太大，按切片再分。

**第3层：表格特殊处理** —— 财报里大量表格，表格有表头和数据行。如果一刀把表格从中间截断，下半截就不知道每列是什么了。所以表格切分时，**每个子表格都复制一份表头**，保证数据行能看懂。这就像切蛋糕时，每一块都要带一点底座。

**第4层：长文本智能断句** —— 有些段落就是一整块纯文本（没有标题、没有表格），超过800字必须切。这时候不能在字中间硬切，而是找"自然断点"：优先在句号后断开，其次换行，再次逗号。相邻chunk之间留128字重叠，防止"832亿"被切成"832"和"亿元"两半。这就像切面包时沿着纹路切，而不是横着拍一刀。

**第5层：父子文档映射** —— 切成小块（500字）是为了精准检索，但检索到小块后，用户需要看到上下文才知道这句话是什么意思。所以每个小块都记录它"属于哪个大块（2000字）"，检索命中小块后，把大块也返回给LLM。这就像查字典先查偏旁（小块），再翻到整页（大块）看完整释义。

**第6层：边界修正** —— 切完后检查：如果某个chunk以逗号开头（说明上一句没说完），就把这个逗号移回上一个chunk的末尾；如果某个chunk以左括号结尾（说明括号里的内容跑到下一个chunk了），就把左括号移到下一个chunk的开头。这就像切完蛋糕后，把掉在盘子外面的奶油抹回去。

#### 一句话总结

> 先按标题分节，再按段落合并，表格保留表头，长文本沿句号断开+重叠拼接，检索小块但返回大块上下文，最后修正断句边界。6层递进，每层解决一个具体的"切错"问题。

#### 面试追问准备

**Q: 为什么不直接用固定长度切分（比如每500字一刀）？**
> 固定长度切分会把一句话切成两半。"招商银行2025年营业收入为832亿元"可能被切成"招商银行2025年营业收入为832"和"亿元"，embedding模型看到"832"不知道是什么，检索就废了。我们的方案是沿语义边界（句号、段落、标题）切分，保证每个chunk语义完整。

**Q: 128字重叠会不会导致冗余？**
> 有一点冗余，但利大于弊。冗余只增加了约16%的存储量，但避免了关键信息被截断。而且embedding模型对重叠部分的向量影响很小——800字的chunk里128字重叠，占比16%，不会改变整体语义方向。

**Q: 父子文档映射为什么不直接用大块检索？**
> 大块检索不精准。一个2000字的大块可能覆盖"营业收入""净利润""资产负债率"三个主题，用户问"营业收入是多少"，检索到这个大块，但LLM要在2000字里找答案，容易混淆。小块（500字）只覆盖一个主题，检索精准；命中后再把大块给LLM看，LLM既有精准定位又有完整上下文。

**Q: 表格切分为什么要复制表头？**
> 财报表格的表头是"项目 | 本期金额 | 上期金额"，如果切分后下半截没有表头，LLM看到"832亿 | 790亿"根本不知道哪个是本期哪个是上期。复制表头后，每个子表格都是自包含的，LLM能直接读懂。

### 6.2 数据清洗管线（已实现）

切片之前，先清洗文本。就像做菜前先洗菜——泥沙（控制字符）、烂叶（重复页眉）、大小不一（全角半角混用）都要先处理掉。

| 步骤 | 通俗解释 | 为什么重要 |
|------|---------|-----------|
| 1. 移除控制字符 | 删掉PDF解析产生的不可见字符（\x00、零宽空格等） | 控制字符会破坏embedding，让向量偏移 |
| 2. 空白规范化 | 多个空格合并为一个，3个以上空行合并为2行 | 减少无效token，节省embedding计算量 |
| 3. Markdown噪声清理 | 图片标记变成"[图片:图表1]"，超链接只保留文字 | 图片URL是噪声，embedding看到URL会误判内容 |
| 4. 重复页眉页脚去重 | 同一行出现3次以上且间隔5行以上→只保留第1次 | PDF每页都有"XX公司2025年年度报告"，不去重会浪费大量token |
| 5. 全半角统一 | "１２３"→"123"，"ＡＢＣ"→"ABC" | 全角半角混用会导致BM25关键词匹配失败 |
| 6. Unicode标准化 | 统一Unicode编码形式 | 同一个字可能有多种编码，不标准化会导致"看起来一样但匹配不上" |

### 6.3 PDF解析降级链（已实现）

PDF解析不是一步到位的——不同PDF质量差异巨大，需要逐级降级：

```
PDF文件
  ↓
第1选择：MinerU云端API → 输出Markdown格式，准确率90.7%
  ↓ （API不可用/额度耗尽）
第2选择：pdfjs-dist本地解析 → 纯文本提取，表格丢失
  ↓ （扫描件/图片PDF）
第3选择：PaddleOCR → 图片OCR识别，最慢但能处理扫描件
```

**Python侧财报专用提取**（更精细的三级降级）：
- 第1选择：pdfplumber表格提取 → 精确识别表格行列结构
- 第2选择：pdfplumber文本提取 → 表格结构丢失但数据还在
- 第3选择：PyMuPDF+PaddleOCR → 扫描件兜底

**为什么需要降级链？** 因为没有一种解析方式能处理所有PDF——排版PDF用MinerU最好，简单文本PDF用本地解析最快，扫描件只能靠OCR。降级链保证任何PDF都能解析出内容，只是质量有差异。

### 6.4 BM25预处理（已实现）

BM25是关键词检索，对文本格式非常敏感。预处理解决3个问题：

| 问题 | 示例 | 解决方式 |
|------|------|---------|
| 千分位逗号 | "825,600"搜"825600"搜不到 | 去掉逗号→"825600" |
| 标点干扰 | "营业收入。"搜"营业收入"匹配度降低 | 标点→空格 |
| 大小写 | "Net Profit"搜"net profit"搜不到 | 统一小写 |

分词用jieba（中文分词效果好），jieba不可用时退化为简单空格分词。

### 6.5 不足与弥补方案

| 不足 | 影响 | 弥补方案 |
|------|------|---------|
| **Token估算粗糙** | `length/1.5`对中英混合不准确 | 引入tiktoken或真实tokenizer |
| **无递归标题层级** | 切片不记录"属于哪个H1下" | metadata中记录parentHeading |
| **表格检测仅限Markdown格式** | 纯文本表格无法识别 | 增加pdfplumber/Camelot表格检测 |
| **图片提取为空** | pdf-parser.ts中images始终为空数组 | 集成图片提取+视觉模型描述 |
| **父子文档映射用内存Map** | 重启丢失 | 持久化到Redis/DB |
| **OCR DPI需手动调参** | 200DPI多页OOM，150DPI识别率下降 | 根据页面复杂度自适应选择DPI |
| **MinerU API无本地缓存** | 同一PDF重复上传浪费额度 | 基于文件hash缓存解析结果 |
| **不支持Word/PPT** | 只处理PDF/MD/TXT | 增加python-docx/python-pptx解析 |
| **BM25预处理破坏数字** | 千分位逗号被移除后数值格式变化 | 数值字段应走SQL精确查询而非BM25 |
| **无切片质量评估** | 不知切片是否语义完整 | 增加相邻切片语义相似度评分 |
| **pdf_extractor仅限财报** | 字段映射硬编码为三张主表 | 通用表格提取与财报专用提取分离 |
| **无增量更新** | 文档更新需全量重新切片入库 | 基于checksum的增量更新 |
