# 评估耗时深度分析

## 概述

以最复杂的 query **L1-001: "中国能建2025年营业收入是多少？"** 为例，总耗时 **150,610ms（约2.5分钟）**。

---

## 第一轮：检索阶段（总耗时 ~7,747ms）

### 步骤1：查询扩展（Query Expansion）
- **做了什么**：将原始查询 "中国能建2025年营业收入是多少？" 扩展为 "中国能建2025年营业收入是多少？ 营收 主营业务收入 营业总收入"
- **耗时**：<1ms（纯字符串操作，同义词词典匹配）
- **数据来源**：`src/server/rag/query/query-expander.ts`，内置金融同义词映射表

### 步骤2：稠密检索（Dense Retrieval / 向量检索）
- **做了什么**：
  1. 调用本地 Embedding 服务 `http://localhost:8011/v1/embeddings`，模型 `bge-m3`，将查询文本转为 1024 维向量
  2. 用生成的向量在 PostgreSQL 中执行 pgvector 余弦相似度查询
- **SQL 语句**（等效）：
  ```sql
  SELECT id, text, document_id, 
         1 - (embedding <=> $queryVector) AS score
  FROM embeddings
  WHERE 1 - (embedding <=> $queryVector) > 0.3  -- 相似度阈值
  ORDER BY embedding <=> $queryVector
  LIMIT 20;
  ```
  - `embedding <=> $queryVector`：pgvector 余弦距离操作符，值越小越相似
  - `1 - (embedding <=> $queryVector)`：转换为相似度分数，范围 [0, 1]
  - `WHERE > 0.3`：过滤掉相似度低于 0.3 的无关文档
  - `LIMIT 20`：返回 top-20 结果（后续 RRF 融合时取 top-10）
- **召回片段**（示例，实际返回 18 条）：
  - 片段1: 中国能建2025年各细分行业营业收入合计约357,036,858千元...（score=0.89）
  - 片段2: 中国能源建设股份有限公司战略性新兴产业营收1,848.5亿元...（score=0.85）
  - ...（共 18 条）
- **耗时**：~3,000ms（Embedding 生成 ~2,000ms + 数据库查询 ~1,000ms）
- **瓶颈**：Embedding 服务调用是 HTTP 请求，每次都需要网络往返

### 步骤3：稀疏检索（Sparse Retrieval / BM25 检索）
- **做了什么**：
  1. 首次运行时从数据库重建 BM25 索引（3395 个文档分块）
  2. 对查询文本进行分词：`[中国能建2025年营业收入是多少, 营收, 营, 收, 主营, 营业, 业务, 务收, 收入, ...]`
  3. 计算 BM25 分数并排序
- **BM25 计算公式**：
  ```
  score(D, Q) = Σ IDF(qi) × (f(qi, D) × (k1 + 1)) / (f(qi, D) + k1 × (1 - b + b × |D| / avgDL))
  ```
  - `IDF(qi)` = log((N - df(qi) + 0.5) / (df(qi) + 0.5) + 1)，N=3395
  - `f(qi, D)`：词 qi 在文档 D 中的词频
  - `k1=1.5, b=0.75`：BM25 参数
  - `|D|`：文档长度，`avgDL=290.25`：平均文档长度
- **召回片段**（示例，实际返回 20 条）：
  - 片段1: 中国能建2025年营业收入...（score=12.5）
  - 片段2: 中国铁建2025年营业收入10,297.845亿元...（score=8.3）
  - ...（共 20 条）
- **耗时**：~3,000ms（索引重建 ~2,500ms + BM25 计算 ~500ms）
- **瓶颈**：首次运行需要从数据库加载全部 3395 个文档分块构建内存索引

### 步骤4：RRF 融合（Reciprocal Rank Fusion）
- **做了什么**：
  1. 将稠密检索 18 条和稀疏检索 20 条结果合并
  2. 按 RRF 公式计算融合分数：`score = 1/(k + rank)`，k=60
  3. 取 top-10 返回
- **RRF 公式**：
  ```
  RRF_score(d) = Σ 1/(60 + rank_dense(d)) + 1/(60 + rank_sparse(d))
  ```
  - `rank_dense(d)`：文档 d 在稠密检索中的排名
  - `rank_sparse(d)`：文档 d 在稀疏检索中的排名
  - `k=60`：平滑参数，减少排名差异的影响
- **耗时**：<10ms（纯内存计算）
- **输出**：10 条融合后的检索结果

### 步骤5：查询间等待
- **做了什么**：等待 8 秒（AGNES AI 20 RPM 限流）
- **耗时**：8,000ms
- **说明**：这是 `run-evaluation.ts` 中设置的 `QUERY_DELAY_MS = 8000`，在第一条查询时不等待

**检索阶段总耗时：~7,747ms**（不含查询间等待）

## 第二轮：答案生成阶段（总耗时 ~43,686ms）

### 步骤1：LLM 调用前等待
- **做了什么**：等待 5 秒（AGNES AI 20 RPM 限流）
- **耗时**：5,000ms
- **说明**：`LLM_CALL_DELAY_MS = 5000`，避免触发 AGNES AI 的速率限制

### 步骤2：LLM 答案生成
- **做了什么**：
  1. 将 10 条检索结果格式化为上下文块
  2. 构造 system prompt + user prompt
  3. 调用 LLM Router，降级链：agnes-2.0-flash(agnes) → qwen-plus(dashscope)
  4. AGNES AI 调用成功，返回 333 字符的答案
- **API 调用**：
  ```
  POST https://agnes.ai/v1/chat/completions
  model: agnes-2.0-flash
  messages: [
    { role: "system", content: "你是一个专业的金融领域问答助手..." },
    { role: "user", content: "以下是相关文档片段：\n\n[文档片段1]\n...\n\n用户问题：中国能建2025年营业收入是多少？\n\n请基于以上文档片段回答问题..." }
  ]
  ```
- **生成结果**：
  > 根据文档片段8，中国能源建设股份有限公司2025年各细分行业营业收入合计约 **357,036,858千元**（即约**3,570.37亿元**）。具体构成如下（单位：千元）：...
- **耗时**：~38,000ms（AGNES AI 响应时间，包含网络往返 + 模型推理）
- **瓶颈**：**这是整个评估最慢的环节**，LLM 推理 + 网络延迟

**答案生成阶段总耗时：~43,686ms**

## 第三轮：评估指标计算阶段（总耗时 ~99,177ms）

### 步骤1：检索指标评估（evaluateRetrieval）
- **做了什么**：
  1. 计算 Hits@5：检查期望答案关键词是否在 top-5 检索结果中出现 → 结果=1
  2. 计算 Context Relevance：使用 `@reaatech/rag-eval-metrics` 库的 ContextPrecisionScorer → 结果=0.841
- **耗时**：~100ms（本地计算，无需 LLM 调用）

### 步骤2：答案质量评估 + Context Recall + 金融指标（并行执行）
- **做了什么**：以下 7 个评估**并行执行**（`Promise.all`）：

#### 2a. evaluateAnswer（答案质量评估）
- **子步骤1**：启发式评估（库评分器）
  - FaithfulnessScorer.score() → 1.0（支持语句 1/1）
  - RelevanceScorer.score() → 0.031（词法相似度 0.052）
  - **耗时**：~500ms
- **子步骤2**：LLM 合并评估（Faithfulness + Relevance + Correctness）
  - 调用 AGNES AI，prompt 包含检索内容 + 生成的答案 + 期望答案
  - 返回 JSON：`{"faithfulness": 0.6, "relevance": 0.8, "correctness": 0.4}`
  - **耗时**：~30,000ms（**LLM 调用，主要瓶颈**）
- **子步骤3**：融合计算
  - Faithfulness = 1.0 × 0.3 + 0.6 × 0.7 = 0.72
  - Answer Relevance = 0.031 × 0.2 + 0.8 × 0.4 + 0.4 × 0.4 = 0.4862
  - **耗时**：<1ms

#### 2b. evaluateContextRecall（上下文召回率）
- **子步骤1**：LLM 评估 Context Recall
  - 调用 AGNES AI，评估检索内容对期望答案关键信息的覆盖度
  - 返回评分：0
  - **耗时**：~20,000ms（**LLM 调用**）
- **子步骤2**：库评分器评估
  - ContextRecallScorer.score() → 0（覆盖事实 0/1）
  - **耗时**：~500ms
- **子步骤3**：融合 + 修正
  - 融合 = 0 × 0.7 + 0 × 0.3 = 0
  - 修正：hitsAtK=1，覆盖率=0.667，修正为 0.667
  - **耗时**：<1ms

#### 2c. evaluateNumericalAccuracy（数值精度评估）
- **做了什么**：提取实际答案和期望答案中的数值，计算匹配度
  - 期望数值：[2025, 3865]
  - 实际数值：[8, 2025, 357036858, 3570.37, ...]（16个）
  - 结果：0.5（2025 匹配，3865 不匹配）
- **耗时**：<1ms（纯本地计算）

#### 2d. evaluateCompliance（合规性评估）
- **子步骤1**：规则匹配（检查承诺收益、推荐时点等违规模式）
  - 结果：无违规
  - **耗时**：<1ms
- **子步骤2**：LLM 评估合规性
  - 调用 AGNES AI
  - 返回：`{"violations": [], "score": 1.0}`
  - **耗时**：~15,000ms（**LLM 调用**）

#### 2e. evaluateHallucination（幻觉率评估）
- **子步骤1**：LLM 评估幻觉率
  - 调用 AGNES AI，检查答案中数值数据点是否能在检索内容中找到来源
  - 返回：`{"ungrounded_points": ["3,570.37亿元", ...], "total_points": 7, "hallucination_rate": 1.0}`
  - **耗时**：~15,000ms（**LLM 调用**）

#### 2f. evaluateRiskDisclosure（风险提示评估）
- **做了什么**：检查 L1-事实提取类别是否涉及投资建议
  - 结果：不涉及，默认 1.0
- **耗时**：<1ms（纯本地计算）

#### 2g. evaluateTimeliness（时效性评估）
- **做了什么**：提取答案和检索结果中的日期，计算最新日期距今天数
  - 结果：未提取到日期，默认 0.5
- **耗时**：<1ms（纯本地计算）

### 步骤3：evaluateAnswerCorrectness（答案正确性评估）
- **做了什么**：
  - 调用 AGNES AI，评估实际答案与期望答案的语义一致性
  - 返回评分：0.6
- **耗时**：~10,000ms（**LLM 调用**）

**评估指标计算阶段总耗时：~99,177ms**（由于并行执行，实际墙钟时间约等于最慢的那个 LLM 调用）

## 总耗时汇总

| 阶段 | 耗时 | 占比 | 主要瓶颈 |
|------|------|------|----------|
| 检索阶段 | ~7,747ms | 5.1% | Embedding 生成 (~2s) + BM25 索引重建 (~2.5s) |
| 答案生成阶段 | ~43,686ms | 29.0% | **AGNES AI LLM 调用 (~38s)** |
| 评估指标计算阶段 | ~99,177ms | 65.8% | **6-7 次 AGNES AI LLM 调用 (~80-90s)** |
| **总计** | **~150,610ms** | **100%** | **LLM API 调用占总耗时 94.9%** |

## 瓶颈根因分析

### 1. LLM API 调用次数过多（核心瓶颈）

每条 query 需要调用 LLM **6-7 次**：

| 调用 | 用途 | 耗时 |
|------|------|------|
| 1 | 答案生成 | ~38s |
| 2 | 合并评估（Faithfulness+Relevance+Correctness） | ~30s |
| 3 | Context Recall 评估 | ~20s |
| 4 | 合规性评估 | ~15s |
| 5 | 幻觉率评估 | ~15s |
| 6 | 答案正确性评估 | ~10s |

虽然步骤 2-5 通过 `Promise.all` 并行执行，但 AGNES AI 有 **20 RPM 限流**，并行请求会被限流排队，实际效果接近串行。

### 2. AGNES AI 限流（20 RPM）

- 免费用户每分钟最多 20 次请求
- 代码中设置了 `QUERY_DELAY_MS = 8000`（查询间 8 秒）和 `LLM_CALL_DELAY_MS = 5000`（LLM 调用间 5 秒）
- 每条 query 6-7 次 LLM 调用 × 5 秒间隔 = 额外 30-35 秒等待

### 3. Embedding 生成

- 每次检索都调用 `http://localhost:8011/v1/embeddings`
- 本地服务但仍有 HTTP 开销，~2s/次

### 4. BM25 索引重建

- 首次运行时从数据库加载 3395 个文档分块构建内存索引，~2.5s
- 后续查询复用索引，但每次新进程启动都需要重建

## 优化建议

### 短期（不改架构）
1. **减少 LLM 调用次数**：将 6-7 次评估 LLM 调用合并为 1-2 次（已有合并评估，但可进一步合并 Context Recall + 合规性 + 幻觉率）
2. **取消不必要的限流等待**：评估场景下使用自有 LLM（dashscope qwen-plus）时，不需要 AGNES AI 的 8s/5s 等待
3. **Embedding 缓存**：对相同查询缓存 embedding 结果

### 中期（架构优化）
4. **评估 LLM 本地化**：评估指标计算使用本地小模型（如 Qwen2.5-7B），避免 API 限流
5. **批量评估**：将多条 query 的评估请求批量发送，减少 API 调用次数
6. **流式评估**：评估指标计算与答案生成流水线化，减少等待

### 长期（系统级）
7. **评估指标本地化**：用规则+小模型替代 LLM 评估，消除 API 依赖
8. **增量 BM25 索引**：避免每次启动重建全量索引
