# 调研1：CRM/OA 接入方案（提交/审批流程）

> 调研日期：2026-08-12
> 数据来源：行业公开资料 + 各厂商开放平台文档（截至 2026-Q2）
> 目标：让智能体从"只做问答"升级为"能提交/审批流程"的 Action Agent

---

## 一、需求本质

当前智能体只做 Q&A（检索→生成），用户要的是 **Action Agent**（理解意图→调用业务系统→执行动作→反馈结果）。

| 维度 | 当前（Q&A） | 目标（Action） |
|------|------------|---------------|
| 输出 | 文本回答 | 文本 + 业务动作（建单/提交/催办/查询状态） |
| 权限 | 只读知识库 | 需要操作 OA/CRM 写权限 |
| 风险 | 答错最多误导 | 误操作会真实发起流程，影响业务 |
| 回滚 | 无需 | 必须支持撤回/取消 |
| 审计 | 仅对话日志 | 必须留痕（谁、何时、替谁、做了什么） |

**核心结论**：这不是"加个工具"那么简单，而是 agent 定位的质变——从"读"到"写"。必须引入**权限模型 + 二次确认 + 审计留痕 + 失败回滚**四件套。

## 二、主流 OA/CRM 开放能力调研

### 2.1 国内 OA（提交流程/审批的主战场）

| 平台 | 开放平台 | 核心能力 | 接入方式 | 适配度 |
|------|---------|---------|---------|--------|
| **钉钉** | 开放平台 > 工作台 > OA 审批 | 创建审批实例/查询审批状态/回调审批结果/获取审批表单模板 | RESTful + 回调 webhook | ⭐⭐⭐⭐⭐ 最全 |
| **飞书** | 开放平台 > 审批 | 创建审批实例/批量审批/订阅审批事件/获取审批定义 | RESTful + 事件订阅 | ⭐⭐⭐⭐⭐ 最全 |
| **企业微信** | 企业微信 API > 审批应用 | 自建应用代提审批/获取审批详情/设置审批模板 | RESTful + 回调 | ⭐⭐⭐⭐ |
| **泛微 e-cology** | e-Bridge / 集成中心 | 流程接口/待办接口/组织同步 | RESTful + WebService | ⭐⭐⭐ 老系统 |
| **致远 OA** | CAP4/集成接口 | 流程发起/流程审批/待办查询 | RESTful | ⭐⭐⭐ |
| **蓝凌** | OpenAPI | 流程/待办/组织 | RESTful | ⭐⭐⭐ |

### 2.2 国内 CRM

| 平台 | 开放能力 | 接入方式 | 适配度 |
|------|---------|---------|--------|
| **销售易** | OpenAPI（线索/客户/商机/合同 CRUD） | OAuth2 + RESTful | ⭐⭐⭐⭐ |
| **纷享销客** | OpenAPI（对象 CRUD + 流程审批） | OAuth2 + RESTful | ⭐⭐⭐⭐ |
| **红圈 CRM** | OpenAPI | RESTful | ⭐⭐⭐ |

### 2.3 国际（备选，金融场景少用）

| 平台 | 能力 | 备注 |
|------|------|------|
| Salesforce | Apex REST / Composite API | 金融行业有合规墙，慎用 |
| HubSpot | CRM API | 偏营销，金融场景少 |
| Microsoft Dynamics | OData Web API | 企业级，但国内金融少用 |

**金融行业结论**：国内金融客户 90%+ 用 **钉钉/飞书/企业微信** 做协同，OA 审批走这三家即可覆盖大部分场景。CRM 在金融行业不是核心（金融有自己的核心系统），但"客户管理/合同审批"会走销售易或自建。

## 三、技术接入方案

### 3.1 推荐架构：MCP 统一接入 + Tool 适配层

```
用户："帮我请三天年假"
  ↓
Agent 意图识别 → 命中"请假提交"技能
  ↓
参数抽取：{类型:年假, 天数:3, 起止日期:?}  ← 缺起止日期，追问
  ↓
用户补全："8月15到17号"
  ↓
Agent 调用 Tool: oa_submit_leave({type:"年假", start:"2026-08-15", end:"2026-08-17"})
  ↓
Tool 适配层 → 路由到用户所属平台（钉钉/飞书/企微）
  ↓
平台 OpenAPI 创建审批实例
  ↓
返回审批单号 + 审批人链 → Agent 告知用户
  ↓
审批状态变更 → 平台回调 webhook → 推送通知给用户
```

### 3.2 三层架构设计

```
┌─────────────────────────────────────────┐
│  Layer 1: Agent 技能层（业务语义）        │
│  - oa_submit_leave（请假）               │
│  - oa_submit_expense（报销）             │
│  - oa_submit_procurement（采购）         │
│  - oa_query_approval_status（查状态）    │
│  - oa_recall_approval（撤回）            │
│  - crm_create_lead（建线索）             │
│  - crm_update_customer（改客户）         │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│  Layer 2: Tool 适配层（平台无关抽象）     │
│  - 统一接口：submitApproval(template,   │
│    formData, approverChain)              │
│  - 统一模型：ApprovalInstance/          │
│    ApprovalStatus/ApproverChain         │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│  Layer 3: 平台 Connector（具体实现）     │
│  - DingtalkConnector（钉钉 OpenAPI）    │
│  - FeishuConnector（飞书 OpenAPI）      │
│  - WecomConnector（企微 OpenAPI）       │
│  - XiaoshouyiConnector（销售易）        │
└─────────────────────────────────────────┘
```

### 3.3 关键技术点

| 技术点 | 方案 | 优先级 |
|--------|------|--------|
| **平台路由** | 用户表加 `oa_platform` 字段，Agent 调用时按用户路由到对应 Connector | P0 |
| **OAuth2 授权** | 每个平台一套 OAuth2，token 存 Redis（按 userId+platform 维度），过期自动刷新 | P0 |
| **审批模板映射** | 配置表 `oa_template_mapping`：业务动作 → 平台审批模板 code | P0 |
| **回调 webhook** | 每个平台注册回调地址，审批状态变更推送到 `/api/oa/callback/:platform` | P0 |
| **二次确认** | 涉及"提交/撤回"类操作，Agent 必须先输出"我将为您提交XX，确认吗？"，用户确认后才执行 | P0 |
| **审计留痕** | 新增 `oa_action_log` 表：userId/agentAction/platform/instanceId/createdAt/result | P0 |
| **失败回滚** | 提交失败时返回明确错误；已提交的撤回走平台撤回 API | P1 |
| **审批人链查询** | 提交前先调平台 API 查询审批流，告知用户"将提交给 A→B→C 审批" | P1 |
| **附件支持** | 报销/采购常带发票附件，支持上传到平台（调平台文件上传 API） | P1 |

## 四、与现有架构的融合点

### 4.1 复用现有能力

| 现有能力 | 复用到 |
|---------|--------|
| LangGraph Agent 编排 | 新增"OA/CRM 技能"节点，复用现有 Agent 框架 |
| ToolRegistry（R016 工具合并） | 新增 oa_* / crm_* 工具，注册到 ToolRegistry |
| Context Compaction（R017） | 长对话中压缩审批历史 |
| Agent 错误恢复（R018） | OA API 调用失败时 checkpoint 重试 |
| Transcript 耗时追踪（R019） | 记录 OA 调用耗时 |
| 合规风控层 | 审批操作必须过合规检查（如金额>50万需人工复核） |
| MCP 双轨设计（ADR-010） | OA/CRM Connector 可作为 MCP Server 接入 |

### 4.2 需要新增

| 新增项 | 说明 |
|--------|------|
| `src/server/oa/` 模块 | Connector 层 + 适配层 |
| `src/server/oa/connectors/` | 钉钉/飞书/企微/销售易 Connector |
| `src/server/oa/skills/` | 业务技能（请假/报销/采购/查状态/撤回） |
| `oa_action_log` 表 | 审计留痕 |
| `oa_template_mapping` 表 | 业务动作→平台模板映射 |
| `oa_account` 表 | 用户绑定哪个平台 + OAuth token |
| `/api/oa/callback/:platform` | 平台回调入口 |
| 前端"我的审批"页 | 展示待办/已办/我发起的 |

## 五、风险与控制

| 风险 | 等级 | 控制措施 |
|------|------|---------|
| Agent 误提交审批（如理解错金额） | 🔴 高 | 二次确认 + 金额/关键字段高亮展示 + 大额人工复核 |
| OAuth token 泄露 | 🔴 高 | token 加密存 Redis + IP 白名单 + 操作审计 |
| 平台 API 限流 | 🟡 中 | 限流器复用现有 rate-limiter + 队列缓冲 |
| 审批模板变更未同步 | 🟡 中 | 启动时校验模板存在 + 定期同步 |
| 回调 webhook 被伪造 | 🔴 高 | 校验签名（每家都有签名机制） |
| 用户越权操作（替别人提交） | 🔴 高 | 严格按 userId 鉴权 + 管理员操作需二次验证 |

## 六、实施建议

### 6.1 分阶段

| 阶段 | 内容 | 周期 | 价值 |
|------|------|------|------|
| Phase 1 | 钉钉 Connector + 请假/报销 2 个技能 + 二次确认 + 审计 | 2 周 | 跑通"提交"闭环 |
| Phase 2 | 飞书 + 企微 Connector + 查状态/撤回 + 回调通知 | 2 周 | 覆盖三大平台 |
| Phase 3 | 销售易 CRM + 客户/线索技能 | 1 周 | 扩展 CRM |
| Phase 4 | 采购/合同/用印等更多流程 + 附件支持 | 2 周 | 全场景覆盖 |

### 6.2 优先级建议

- **P0**：钉钉 Connector（金融客户最多用钉钉）+ 请假 + 报销 + 二次确认 + 审计
- **P1**：飞书 + 企微 + 查状态 + 撤回 + 回调
- **P2**：CRM + 更多流程类型 + 附件

### 6.3 不建议做的

- ❌ 不要自己实现工作流引擎（OA 平台已有，复用即可）
- ❌ 不要试图替代 OA 的审批 UI（用户在 OA 里审批，agent 只负责"提交"和"查状态"）
- ❌ 不要让 agent 自动审批（审批必须人来做，agent 只是"提交者"和"查询者"）

## 七、与 V3.0 的关系

这是 V3.0 的**核心新增能力**之一，定位为"从 Q&A Agent 升级为 Action Agent"。建议作为 V3.0 的旗舰功能，但分阶段交付（Phase 1 先上）。
