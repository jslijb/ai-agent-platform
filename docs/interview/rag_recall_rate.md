## 一、数据与索引优化：打好地基

这是提升召回率的基础。数据本身质量不高或索引构建不当，后续的检索策略再优秀也会事倍功半。本章节覆盖从原始文档到可检索向量索引的完整链路：**清洗 → 分块 → 向量化 → 元数据标注**。

### 1.1 文档清洗与结构化

这一步的核心目标只有一个：**将原始文档（PDF、Word、网页等）转化为干净、语义完整、且带有上下文标记的纯文本，为后续的分块做准备。**

#### 第一步：格式解析与内容提取

将不同格式的文件统一提取为纯文本，并识别出表格、图片中的文字。这一步远比"把文字拿出来"复杂——**PDF 和 Word 文档中隐藏着大量的结构信息和图文关系，如果提取时丢失，后续的分块和检索质量会大打折扣。**

##### PyMuPDF（fitz）提取 PDF 的能力与局限

| 能力维度 | 支持情况 | 说明 |
|:---|:---|:---|
| **纯文本提取** | ✅ 支持 | 速度快、不易乱码，按页面逐页提取 |
| **表格提取** | ⚠️ 部分支持 | `page.find_tables()` 可提取简单表格，但合并单元格、跨页表格需额外处理 |
| **扫描版 PDF** | ❌ 不支持 | 必须接入 OCR 引擎（如 PaddleOCR） |
| **层次结构（章节/小节/段落）** | ❌ 无法直接提取 | PDF 没有原生的"章节"概念，只有视觉坐标上的文字块 |
| **目录（书签/大纲）** | ⚠️ 部分支持 | `doc.get_toc()` 可提取书签大纲，但很多 PDF 没有书签或书签不完整 |
| **图片提取** | ✅ 支持 | `page.get_images()` 可提取嵌入图片，但**无法获取图片与正文的位置关系** |
| **图片注解/描述文字** | ❌ 无法自动关联 | 图片上方/下方的描述文字与图片之间没有绑定关系，需手动根据坐标推断 |
| **页码与位置** | ✅ 支持 | 可获取文字块的坐标 (x0, y0, x1, y1)，用于推断阅读顺序和图文关系 |

**PDF 层次结构提取的核心难题**：

PDF 本质是一个**排版描述语言**，不是结构化文档格式。它记录的是"在坐标 (x, y) 处绘制文字 ABC"，而不是"这是第三章第二节的第一段"。因此：

- **没有书签的 PDF**：完全无法自动识别章节边界。只能通过启发式规则猜测——比如字号比正文大、加粗、居中的文字可能是标题，但这在排版多样的文档中极不可靠。
- **有书签的 PDF**：`doc.get_toc()` 可以获取书签树（如 `[1, "第3章 优化策略", 42]` 表示第1级标题、第42页），但书签通常只到章节级别，不到段落级别。
- **需要 LLM 辅助**：对于层次结构不明显的文档（如没有明确标题标记的连续论述），可能需要将全文送入 LLM，让其理解语义后生成完整的内容脉络和大纲。

**Word 转 PDF 时书签的保留与丢失**：

这是一个极易被忽视的关键问题。Word 文档中的标题样式（Heading 1/2/3）在转 PDF 时，**能否变成 PDF 书签，完全取决于转换方式**：

| 转换方式 | 书签是否保留 | 说明 |
|:---|:---|:---|
| **Word "另存为 PDF"** | ✅ 保留 | 默认将 Heading 样式转为 PDF 书签，`doc.get_toc()` 可提取 |
| **Word "打印为 PDF"（Microsoft Print to PDF）** | ❌ 丢失 | 打印驱动只保留视觉内容，不生成书签结构 |
| **WPS 导出 PDF** | ⚠️ 视设置而定 | 需要在导出设置中勾选"生成书签"选项 |
| **LibreOffice 导出 PDF** | ✅ 保留 | 默认将 Heading 样式转为书签 |
| **在线转换工具（SmallPDF、iLovePDF 等）** | ❌ 通常丢失 | 大多数免费工具只做视觉转换，不保留结构信息 |
| **Python `docx2pdf` 库** | ✅ 保留 | 底层调用 Word COM 接口，等同于"另存为 PDF" |
| **Python `pdfkit`/`wkhtmltopdf`** | ❌ 丢失 | 从 HTML 中转，无结构信息 |

**实际影响**：同一个 Word 文档，用不同方式转出的 PDF，提取结果可能天差地别：
- 用"另存为 PDF"转出的：`doc.get_toc()` 返回完整的三级书签树，章节边界清晰。
- 用"打印为 PDF"转出的：`doc.get_toc()` 返回空列表，所有标题都变成了普通文字，只能靠启发式规则猜测。

**应对策略**：
1. **优先获取原始 Word 文件**：如果源文件是 Word，直接用 `python-docx` 提取，避免转 PDF 过程中的信息丢失。
2. **检查 PDF 书签完整性**：拿到 PDF 后先调用 `doc.get_toc()` 检查书签。如果返回空列表或只有一级书签，说明转换时结构信息已丢失，需要回退到启发式规则或 LLM 辅助。
3. **建立转换规范**：如果业务流程中需要 Word 转 PDF，强制要求使用"另存为 PDF"方式，并在转换设置中勾选"创建书签"。

**图片与文字关系提取的核心难题**：

PDF 中的图片和文字是独立的对象，没有"这张图片的描述是……"这种绑定关系。常见场景：

- **图片注解**：图片上方或下方有一行小字"图3-1：召回率优化路径"，这行文字与图片之间没有结构关联，只是视觉上相邻。
- **正文引用**：正文中写"如图3-1所示"，这个引用与实际图片之间也没有链接。
- **提取方案**：只能通过**坐标推断**——提取图片的边界框坐标，然后查找同一页面中 y 坐标紧邻图片上方或下方的文字块，将其标记为图片描述。但这种启发式方法在复杂排版中容易出错。

##### python-docx 提取 Word 文档的能力与局限

| 能力维度 | 支持情况 | 说明 |
|:---|:---|:---|
| **纯文本提取** | ✅ 支持 | 遍历 `doc.paragraphs` 即可 |
| **层次结构** | ✅ 支持 | 通过 `paragraph.style.name` 判断标题层级（Heading 1/2/3） |
| **目录/大纲** | ⚠️ 部分支持 | Word 有原生的标题样式，但部分文档用加粗/字号代替标题样式，无法自动识别 |
| **表格提取** | ✅ 支持 | `doc.tables` 可直接访问表格对象，支持合并单元格 |
| **图片提取** | ⚠️ 部分支持 | 只能获取图片的 URI/关系 ID，需借助 `requests`/`Pillow` 下载 |
| **图片注解/描述文字** | ❌ 无法自动关联 | 图片与周围文字没有绑定关系，需手动推断 |
| **图片位置** | ⚠️ 部分支持 | 可获取图片所在段落，但无法精确定位"图片在段落中的哪个位置" |
| **列表结构** | ✅ 支持 | `'List Bullet'`/`'List Number'` 样式可识别 |

**Word 层次结构提取的核心难题**：

Word 比 PDF 好在它有原生的样式系统（Heading 1/2/3），但实际文档中大量存在以下问题：

- **样式不规范**：很多作者不用标题样式，而是用"加粗+大字号"来表示标题。`paragraph.style.name` 返回的是 `'Normal'`，无法通过样式判断层级。
- **样式混用**：同一文档中，部分章节用了 Heading 样式，部分章节用了自定义样式或手动加粗。
- **应对方案**：对于样式不规范的文档，需要**回退到启发式规则**——检测段落的字体大小、是否加粗、是否居中等视觉特征来推断标题层级。更可靠的方案是用 LLM 对全文进行语义理解后生成大纲。

**图片与文字关系提取的核心难题**：

与 PDF 类似，Word 中图片与描述文字之间也没有结构绑定。但 Word 略优于 PDF：

- 图片是内嵌在段落中的，可以通过遍历段落找到包含图片的段落。
- 图片的"题注"（Caption）在 Word 中有专门的样式 `'Caption'`，如果作者使用了题注功能，可以通过样式识别。
- 但大多数文档中，图片描述只是普通段落，没有使用题注样式。

##### PDF vs Word 提取能力对比

| 维度 | PDF (PyMuPDF) | Word (python-docx) |
|:---|:---|:---|
| **层次结构** | ❌ 无原生支持，依赖书签或启发式猜测 | ✅ 有标题样式系统，但文档中常不规范 |
| **图文关系** | ❌ 需坐标推断，不可靠 | ⚠️ 图片在段落内，题注有样式，但不一定被使用 |
| **表格** | ⚠️ 简单表格可以，复杂表格需额外处理 | ✅ 原生支持，合并单元格可处理 |
| **排版保真度** | ✅ 精确到像素 | ❌ 只能获取逻辑结构，无法获取精确排版 |
| **扫描件** | ❌ 需 OCR | ❌ Word 不存在扫描件问题 |
| **推荐策略** | 有书签→用书签；无书签→LLM 辅助生成大纲 | 有标题样式→用样式；无样式→启发式规则+LLM 辅助 |

##### 两种极端的文档结构场景

**场景一：结构清晰的文档（有大纲/目录）**

这类文档有明确的标题层级（如"第3章 → 3.1节 → 3.1.2小节"），提取相对简单：
- PDF：优先用 `doc.get_toc()` 提取书签树，再按书签定位到对应页面的文本。
- Word：遍历段落样式，按 Heading 1/2/3 构建层级树。

**场景二：结构模糊的文档（无大纲、无标题标记）**

这类文档是连续的论述体，没有明确的章节划分。例如一份政策解读文档，全文 5000 字只有段落，没有标题。这种情况下：
- **启发式规则失效**：没有字号差异、没有加粗标记，无法通过视觉特征判断层级。
- **必须依赖 LLM 语义理解**：将全文送入 LLM，让其分析语义后生成大纲。Prompt 示例：
  ```
  请分析以下文档内容，生成一个层次化大纲，标注每个章节/小节的起始位置和主题摘要。
  输出格式：JSON，包含 level、title、summary、start_paragraph_index 字段。
  ```
- **工程权衡**：LLM 调用有成本和延迟，但对于结构模糊的文档，这是唯一可靠的方案。可以设置阈值——当启发式规则无法识别出任何标题时，触发 LLM 辅助。

##### 网页（HTML）提取

- 使用 **BeautifulSoup**，只提取 `<p>`、`<h1>`~`<h6>` 等正文标签，**剔除** `<script>`、`<style>` 和导航栏广告。
- HTML 的层次结构由标签天然定义（`<h1>` → `<h2>` → `<h3>`），提取最简单、最可靠。
- 图片的 `alt` 属性可直接作为图片描述，图文关系最清晰。

**PyMuPDF 提取 PDF 表格的注意事项**：

- **表格提取后，上下文需要主动保留**：PyMuPDF 本身在提取表格时，**不会自动关联**表格的标题、前文描述等上下文信息。提取出的只是孤立的表格数据，因此需要在代码中手动将这些上下文信息与表格数据拼接在一起。
- **提取表格数据时，要注意"引用陷阱"**：在遍历 PDF 页面提取表格时，如果写法不当，可能会导致所有表格数据都指向最后一页的内容。
  - ❌ **错误做法**：先收集所有表格的**对象引用**，再统一处理。
  - ✅ **正确做法**：在遍历到每一页时，**立即调用 `.extract()` 方法**将表格数据提取为独立的 Python 数据结构（如列表或 Pandas DataFrame）并保存。

**更高层的封装库**：

- 对于 PDF，可以关注 **`PyMuPDF4LLM`**，它是 PyMuPDF 的官方扩展，能更方便地将 PDF 转换为结构化的 Markdown、JSON 等格式，专为 RAG 和 LLM 应用优化。
- 对于结构提取，**`unstructured`** 库提供了更高级的文档解析能力，能自动识别标题、列表、表格等元素类型，并输出带标注的结构化数据。

#### 第二步：噪声清洗（清洗"垃圾"）

去掉所有对语义理解无益的字符，防止干扰 Embedding 模型。

- **特殊字符**：使用正则表达式 `re.sub(r'[^\u4e00-\u9fa5a-zA-Z0-9，。！？；：]', ' ', text)` 过滤乱码、emoji表情和奇怪的制表符（根据业务语言调整保留范围）。
- **无意义元素**：删除页眉、页脚、页码、版权声明、超长URL链接（除非是核心内容）。
- **多余空格与换行**：将连续的多个空格或换行符压缩为单个，避免因排版错乱产生空分块。

#### 第三步：文本规范化（统一格式）

让文字表达标准化，消除排版带来的歧义。

- **全角/半角统一**：将英文标点（, .）和数字统一转为半角，中文标点（，。）统一转为全角（推荐使用 `unicodedata.normalize` 或简单替换映射）。
- **特殊符号转译**：将"→"、"●"等列表符号统一替换为标准的"-"或"*"；将"\u3000"（全角空格）转为普通空格。
- **日期与数字格式化**：将"二四年六月"统一转为"2024年6月"，保证时间线的可检索性。

#### 第四步：结构标记与元数据保留（关键步骤）

保留文档的层级逻辑（标题、段落、列表），并在文本块中嵌入上下文信息，防止分块后"断章取义"。

- **添加层级前缀**：在处理时记录当前标题栈。例如，将纯文本 `"召回率提升"` 改写为 `"章节：3.2 | 子章节：优化策略 | 内容：召回率提升..."`，把这些信息直接拼接到正文前。
- **表格结构化**：不要按行提取表格，应转为 **Markdown 表格格式** 或 `列名：值` 的键值对形式，保留行列对应关系。
- **注入元数据**：在输出的文本开头，强制拼接文件级信息，如 `[文档ID: xxx] [发布时间: 2026-01] [类别: 技术文档]`，这能帮助后续检索器进行过滤。

**工具推荐速查表**：

| 任务 | 推荐Python库 |
| :--- | :--- |
| 复杂PDF/布局保留 | `pdfplumber`（比PyMuPDF更擅长提取表格） |
| OCR识别 | `PaddleOCR`（中文效果最佳） |
| 正则清洗万能工具 | `re` 标准库 |
| Markdown转换 | `markdown-it-py`（将富文本转回标准Markdown） |

**最后提示**：清洗完成后，请务必**抽样检查**（尤其是特殊符号和表格），确保清洗逻辑没有误删关键数学符号（如">"、"<"）或专业术语中的连字符。这一步做得越干净，后续的混合检索和重排序才会越有效。

### 1.2 文本分块策略

分块过大信息会被稀释，过小则会导致语义破碎。分块策略直接决定了向量索引的质量。

#### 核心认知：不要使用固定 Chunk Size

不要使用固定 Chunk Size（如 512 token），那是 BERT 时代遗留的技术惯性。应优先按文档的语义边界（段落、章节）切分，仅对超长段落设置硬上限作为兜底。

**为什么"按段落切分"比"按长度切分"更合理？**

- **语义完整性**：文档作者写段落时，天然把一个完整的子话题放在一段或连续几段里。按长度硬切（比如第500字处切断）会把一个完整的推理链条拦腰斩断，导致向量化时丢失"前因后果"。
- **检索粒度的匹配**：用户问一个问题，通常期望答案是**一个完整的知识点**，而不是半个句子。段落天然就是知识点的最小单元。

**"表示坍缩"现象**：大多数 Embedding 模型在处理长文本时，会倾向于将注意力平均化，导致文本头尾的关键信息被"淹没"在中间。一个 8192 tokens 的段落向量，在计算相似度时，用户的 Query 可能只问其中某一页的知识，但向量相似度会被其他无关章节带偏，导致**检索精度严重下降**。

#### 动态边界检测 + 硬上限截断

不使用固定数字，而是使用一套**"动态边界检测 + 硬上限截断"**的规则：

| 策略层级 | 判断逻辑 | 如何操作 |
| :--- | :--- | :--- |
| **一级切分（主策略）** | 检测文档的**结构边界** | 优先按 `H1/H2/H3` 标题切；无标题则按 `\n\n`（双换行）切。 |
| **二级切分（辅助策略）** | 检测**语义边界** | 如果一级切出的块 > **2048 tokens**，则退一步按 `\n`（单换行）或 `。！？`（完整句子）切断。 |
| **三级切分（兜底策略）** | 检测**绝对硬上限** | 如果段落极其冗长（如法律条款，无任何换行）且 > **8192 tokens**，此时**只能硬切**。但硬切后，需要将前一块的后10%内容和后一块的前10%内容重叠（Overlap），以保住边界上下文。 |

**项目初始启动准则**：

1. **切分单元**：`TextSplitter` 参数设为 `separators=["\n\n", "\n", "。"]`，**不设固定长度**，优先保持语义完整。
2. **最大上限**：仅设置一个 `max_length=2048` 的**绝对安全阀**（针对极少数超长段落），超过则按句子边界切。
3. **元数据绑定**：每个切出来的块，都必须绑定 `chapter_title`（章节名）和 `paragraph_index`（段落序号），用于后续多路召回时的重排序权重加分。

**一句话**：**让文档作者定义的"段落"来决定边界，让 LLM 的上下文窗口去适应段落的长度，而不是让段落去适应一个僵硬的数字。**

---

### 1.3 多粒度分块（父子块索引）

这是经典的 **"父子块索引"（Parent-Child / Small-to-Big）** 策略，核心逻辑是：**用"小粒度"去匹配，用"大粒度"去生成**。

#### 物理存储结构

- **父块（Parent / 大粒度）**：按章节、大段落切分，**尺寸较大**（如 1024~2048 tokens）。不参与向量检索，只作为"背景上下文"存储在文档数据库（如 MongoDB 或 Redis）中，并赋予唯一的 `parent_id`。
- **子块（Child / 小粒度）**：**在父块内部**，按句子或小段落再次切分，**尺寸较小**（如 128~256 tokens）。这些子块会被 Embedding 并存入向量库。
- **映射关系**：向量库中的每一个子块向量，都必须携带一个元数据字段 `parent_id`，指向其归属的父块。

#### 构建流程示例

```text
原始文档 -> 按章节粗切（得到父块A，ID=001）
父块A（1000字） -> 按句子/段落细切（得到子块A1, A2, A3）
存储父块A全文至 KV存储（Key=001, Value=父块全文）
将子块A1,A2,A3 分别向量化，入库（附加字段 parent_id=001）
```

#### 检索与匹配流程

1. **第一阶段：向量召回（定位子块）**
   - 用户输入 Query，Embedding 后去向量库检索。
   - 召回 Top-K（比如 Top-30）个**最相似的子块（Child）**。此时由于子块小、语义纯净，能精准命中文档中的"关键句子"。

2. **第二阶段：父块映射与去重（跨级跳跃）**
   - 提取这30个子块各自的 `parent_id`。
   - 假设30个子块只归属于10个不同的父块。**执行去重与聚合**：按 `parent_id` 分组，只保留这10个不重复的父块ID。

3. **第三阶段：上下文重组（替换与注入）**
   - **关键操作**：**丢弃**子块的原文，用这10个父块的**全文**去替换子块。
   - 从 KV 存储中拿出这10个父块的大段文本，按它们在原文档中的**原始排序**重新拼接成完整的上下文窗口。

4. **第四阶段：送入 LLM**
   - 将重组后的大文本和用户的 Query 一起送给大模型生成答案。

#### 三大优势

- **命中率高**：小颗粒子块能精准命中"召回率"这个词，不会被前后大段无关文字稀释掉向量相似度。
- **语义完整**：送入 LLM 的是完整的父章节，包含了前因后果、背景定义，大模型不会断章取义。
- **解决"包围盒"问题**：如果一篇文档同时包含"召回率提升方法"和"召回率失败案例"，子块能精准定位到"方法"章节，而不会错误地匹配到"失败案例"章节里的相关词。

#### 工程落地注意事项

- **上下文窗口限制**：如果 Top-30 子块映射出了10个父块，父块太大导致总 tokens 超过 LLM 上下文限制怎么办？引入 **"二次重排（Rerank）"**。在映射出父块后，用 Rerank 模型仅对这10个父块按其与 Query 的相关性重新打分，**只取得分最高的前3~5个父块**送入 LLM，强行截断。
- **Overlap 设置**：在切分子块时，子块之间依然要保留少量重叠（如10%），防止跨子块的上下文在映射回父块前，向量检索时出现断裂。

---

### 1.4 Embedding 模型选择

Embedding 是将文本转化为向量的过程，是构建向量索引的核心环节。Embedding 模型的质量直接决定了召回率的上限——**数据索引时用它在入库前向量化，查询时用它将 Query 向量化，两端使用同一个模型。**

#### 模型选型参考

- **中文通用场景**：可选用 `BGE-large-zh`。
- **追求极致效果**：可考虑 `text-embedding-3-large` 等商业模型。
- **资源有限场景**：可选用 `M3E-large` 等轻量模型。
- **最佳实践**：用你的测试集跑几个模型，选择效果最好的那个。如果预算允许，用领域内的问答对微调 Embedding 模型，收益可达2%左右。

---

### 1.5 元数据与索引

#### 元数据体系：6类核心字段

根据国际标准 ISO/IEC 11179 及 RAG 实践，元数据可分为六大核心类型：

| 类型 | 说明 | 常见字段示例 |
|:---|:---|:---|
| **描述型元数据** | 描述文档内容的核心字段，直接影响召回率 | 标题、摘要、关键词 |
| **管理型元数据** | 技术属性与维护信息 | 文件格式、编码方式、创建时间、修改时间、版本号 |
| **结构型元数据** | 文档的层级关系 | 目录层级、章节关系、段落编号 |
| **权限型元数据** | 访问控制与安全分级 | 保密等级（公开/内部/机密）、ACL权限 |
| **标记语言型元数据** | 语义标注与增强 | HTML/Markdown标签、专业术语标注 |
| **关联型元数据** | 知识网络与引用关系 | 引用关系、同义词库、知识图谱三元组 |

**基础层推荐8类核心字段**：文档类型、业务领域、版本号、创建时间、修改时间、保密等级、关联项目、知识标签。

#### 标签体系的3层架构

标签是元数据的具体实例化，建议构建**三级标签架构**：

- **基础标签**：文档类别、品牌、作者等通用属性
- **领域标签**：材质、尺寸、适用人群等业务相关属性
- **场景标签**：节日促销、礼品推荐等动态场景属性

标签的生成可采用**动态标注**方式，结合 BERT 等预训练模型自动从文档中提取。

#### 元数据存储在哪里？

元数据采用**与向量关联存储**的方式：

- **向量数据库内联存储**：在存储向量的同时，将元数据作为结构化字段关联存储，支持"向量相似性检索 + 元数据精准过滤"的复合查询。
- **独立元数据索引**：构建轻量级元数据索引，由标签和元数据约束明确定义。

**检索流程**：先基于元数据条件快速过滤无关文档（粗筛），再对结果进行语义相似度计算（精排）。这种方式可使有效文档召回率从38%提升至82%，同时减少76%的向量计算量。

#### 书籍/长篇文档的层次化索引

**核心思路**：通过解析文档的天然结构（章节标题、列表层级、表格关系）建立**树状索引**，实现"**章节定位 → 内容导航 → 答案生成**"的三阶段推理。

**构建步骤**：

1. **解析文档结构树**：提取文档的层级结构，建立索引树：
   ```
   根文档
   ├── 第1章（标题、摘要）
   │   ├── 1.1 节
   │   │   └── 段落块
   │   └── 1.2 节
   ├── 第2章
   │   ├── 2.1 节
   │   └── 2.2 节
   └── 附录
   ```

2. **为每个节点生成摘要**：对每个章节、小节生成**结构化摘要**和元数据，构建一个**结构化检索层**，根据用户查询动态拉取相关文档。

3. **存储层级关系**：
   - **父节点**存储：章节标题、摘要、元数据、子节点列表
   - **叶节点**存储：具体文本块、向量、所属父节点ID

**一套代码如何复用不同结构的文档？**

核心原则：**不依赖固定的章节编号，而是依赖标题层级特征**。

```python
# 伪代码：通用的层级解析器
def parse_hierarchy(doc):
    # 1. 检测标题级别（基于字体大小、加粗、编号模式等特征）
    headings = detect_headings(doc)  # 返回 [(level, title, position), ...]
    
    # 2. 构建层级树（不预设章节名，只依赖level关系）
    tree = build_tree(headings)  # level 1 -> 一级标题, level 2 -> 二级标题...
    
    # 3. 为每个节点分配内容（从当前标题到下一个同级/更高级标题之间）
    for node in tree:
        node.content = extract_content(node.position, next_sibling.position)
    
    return tree
```

**关键设计**：
- 标题检测基于**样式特征**（字体大小、加粗、缩进、编号模式），而非固定的"第X章"字符串。
- 层级关系由**标题的 level 数值**决定，不依赖具体的章节名称。
- 不同文档（技术手册、小说、法律文书）只要标题有层级特征，同一套代码即可复用。

### 1.6 表格检索

#### 表格解析面临的挑战

传统方案在处理复杂表格时常见三大问题：
- **结构失真**：合并单元格被拆分，行列关系断裂
- **语义丢失**：数值单位与数值分离，关键指标无法关联
- **跨页断层**：分页表格被截断，表头重复或缺失

#### 各类复杂表格的处理方案

**（1）二维标准表格**

最简单的情况，直接提取为 DataFrame 结构：
```python
# PyMuPDF提取表格
tables = page.find_tables().tables
for table in tables:
    df = pd.DataFrame(table.extract())  # 转为DataFrame
```

**（2）合并单元格**

**处理思路**：检测合并单元格的覆盖范围，拆分为多个独立单元格并**填充重复值**。例如，一个横跨3列的合并单元格，在对应行生成3个相同值的单元格。

**技术实现**：基于**网格化合并检测算法**，将表格区域映射为虚拟网格矩阵，通过分析单元格的坐标边界（而非仅依赖文本内容），精确识别合并区域。

**（3）跨页表格**

**处理思路**：采用**渐进式匹配策略**，解决三个关键问题：
- 判断相邻页面的表格片段是否属于同一个逻辑表格
- 识别续表的表头（续表通常只保留数据行，不重复表头）
- 将数据行正确对齐

**技术实现**：通过**表头指纹**（表头文本的哈希值）识别跨页表格，实现分页数据拼接。

**（4）横向表格（表格太宽，竖着放不下）**

**处理思路**：
- 检测页面旋转角度（90°或270°）
- 在解析前对页面进行**旋转校正**，将横向表格转为正向
- 或提取时标记 `orientation: "landscape"` 元数据，检索时特殊处理

#### 表格的向量化与检索策略

**策略一：行级拆分（推荐）**

将每行数据重构为 **"列头: 值"** 的结构化文本：
```
原始表格：
| 产品ID | 产品名称 | 单价 | 年份 |
| P001   | 手机    | 999  | 2025 |

转换为：
"产品ID: P001，产品名称: 手机，单价: 999元，年份: 2025年"
```

**优势**：保留列头与行数据的语义关联，支持"产品A的单价"这类精准查询。

**策略二：表头独立索引**

- 将**表头**单独提取并向量化
- 检索时先匹配表头，定位到正确的表格，再在表格内检索具体数据

**策略三：表格摘要+全文**

- 为每个表格生成**摘要**（表格主题、列名、关键数据范围）
- 摘要用于粗筛，命中后再返回完整表格内容

#### 实操工具推荐

| 场景 | 推荐方案 |
|:---|:---|
| 简单表格 | PyMuPDF + Pandas |
| 合并单元格/复杂表头 | 网格化合并检测算法 |
| 跨页表格 | 表头指纹匹配 + 渐进式拼接 |
| 生产级复杂表格 | TextIn（实测表格准确率达99%）或 RAGFlow |

**面向 RAG 的表格解析，应重点看四件事**：
1. **结构是否正确**：表头层级、行列边界、合并单元格、跨页拼接是否保留
2. **关系是否正确**：每个数字是否挂在正确的字段、表头和上下文下
3. **数值是否精准**：数值型数据的识别误差率需控制
4. **上下文是否关联**：表格内容与前后文描述是否建立语义关联

## 二、查询与检索策略优化：精准定位

数据索引建好后，接下来优化用户的查询方式和检索方式。这是提升召回率最直接、见效最快的手段。

### 2.1 查询改写与扩展

用户的原始问题可能不够精确。

- **查询改写**：用大模型将模糊问题清晰化（如将"休假政策"改写为"员工有多少天年假？"）。
- **查询扩展**：增加同义词、相关词，或将复杂问题拆解成多个子问题分别检索。
- **HyDE (假设性文档嵌入)**：让大模型先根据问题生成一个"假设性答案"，再用这个答案去检索，能有效弥合问题与文档的表述差异。

---

### 2.2 混合检索 (Hybrid Search)

**这是性价比最高的优化手段**。单一的向量检索擅长语义理解，但可能漏掉精确关键词；传统的关键词检索（如 BM25）则相反。

- **做法**：同时进行向量检索和关键词检索，然后用**倒数排名融合（RRF）** 等算法合并两路结果。有案例显示，仅此一步就能将召回率从83%提升到88%。

---

### 2.3 多路召回

在混合检索的基础上，可进一步引入基于知识图谱的检索或对表格、图片等特殊内容的检索，进一步扩大召回面。

---

### 2.4 Top-K 设置

Top-K 是检索阶段的核心参数：**从向量库中取出多少条候选结果**。取少了会漏掉相关文档，取多了会引入噪声、拖慢后续环节。这里分两个阶段说明。

#### 粗排 Top-K（向量检索阶段）

粗排的目标是**广撒网**，把可能相关的文档都捞进来。

- **起始范围**：通常从 **100 ~ 1000** 开始尝试，数据量越大取越多。
- **确定方法**：准备一批测试 Query，逐步增大 K 值，观察召回率曲线。当 K 值增大到召回率几乎不再提升时（拐点），就是性价比最高的取值。
- **经验参考**：粗排 K 值通常约为精排 K 值的 30 倍。

**一句话：粗排要"大"，大到刚好把所有可能相关的文档都捞进来。**

#### 精排 Top-K（送入 LLM 阶段）

精排的目标是**择优录取**，只把最相关的文档送入大模型。

- **起始范围**：**5 ~ 20** 之间。太少会丢信息，太多会触发"Lost in the Middle"问题（模型对长文本中间部分关注度下降）。
- **按问题类型动态调整**：
  - 简单事实型问题（如"XX公司CEO是谁？"）：**3 ~ 5 个**
  - 复杂分析型问题（如"总结这份财报的核心风险"）：**10 ~ 20 个**
- **最终上限**：受 LLM 上下文窗口限制。可用公式估算：`可送入文档数 = (模型上下文上限 - Prompt指令) / 文档平均长度`。

**一句话：精排要"精"，在保证信息不缺失的前提下，越少越好。**

#### 父子块模式下的取数逻辑

在父子块架构中，需要决定三个数字，决策顺序是**从后往前反推**：

1. **先定"送入 LLM 的父块数"**：由 LLM 上下文窗口决定。例如窗口留出 7000 tokens 给文档，父块平均 1500 tokens，则最多送 4 个父块。
2. **再定"精排后保留的子块数"**：要保证这 4 个父块都能被覆盖。假设每个父块平均含 5 个子块，考虑冗余（扩散系数 2~3 倍），精排后保留约 `4 × 5 × 2.5 = 50` 个子块。
3. **最后定"向量检索的子块数"**：广撒网，取精排数的 3 倍以上，或通过召回率拐点测试确定，通常在 150 ~ 250。

---

## 三、重排序与评估迭代：优中选优与持续改进

召回和排序是两个不同的阶段。召回阶段的目标是"广撒网"，排序阶段则是"择优录取"。

### 3.1 重排序 (Rerank)

在初步召回一个较大的候选集（如50或100个文档）后，用一个更强大、更精确的模型（如 **Cross-Encoder**）对这些文档进行重新打分和排序。

- **好处**：能显著提升**首位命中率**（即最相关文档排第一的概率），改善用户体验。有案例显示，增加 Reranker 后，首位命中率可从45%提升到68%。

#### 多粒度模式下 Rerank 的具体位置

在父子块架构中，Rerank 必须插在 **"子块向量检索"** 和 **"映射回父块"** 这两个动作**之间**。

错误的做法是先映射回父块再做 Rerank（此时文本太长，Rerank 模型容易失效）。正确的流程如下：

1. **子块粗筛**：Query 检索向量库，召回 Top-100 个最相似的**子块（Child）**。
2. **【Rerank 介入】**：将这100个子块的文本，与 Query 一起送入 Cross-Encoder（重排序模型）进行精确语义打分，按新分数重排。
3. **筛选截断**：只取 Rerank 后得分最高的 **Top-N 个子块**（例如只取前20个）。
4. **映射回父块**：提取这20个子块的 `parent_id`，去重，得到最终的3~5个父块。
5. **送入 LLM**：将筛选后的父块全文拼接进 Prompt。

#### Rerank 具体在对"谁"操作？

**核心结论**：Rerank 操作的对象是 **"子块（Child）"**，而非"父块（Parent）"。

因为 Rerank 模型（如 `bge-reranker-v2-m3`）本质是 Cross-Encoder，它需要将 Query 和候选文档拼接成一个长序列进行注意力计算，其复杂度是 O(n²)。**它无法高效处理上千 token 的长文本**。

- 子块（256 tokens）长度适中，Rerank 模型可以轻松跑100条，打分极其精准。
- 如果先映射成父块（2048 tokens），Rerank 模型跑10条就可能爆显存或耗时剧增，完全失去工程可行性。

#### 多粒度下的 Rerank vs. 传统平铺模式的 Rerank

| 维度 | 传统平铺模式（Flat） | 多粒度父子模式（Parent-Child） |
| :--- | :--- | :--- |
| **Rerank 时机** | 向量检索直接召回 Top-K 文档块 → 直接对这 K 个块 Rerank。 | 向量检索召回子块 → **Rerank 子块** → 再映射成父块。 |
| **Rerank 对象** | 最终送入 LLM 的候选块本身。 | **中间态**的子块（仅作为指针，不是最终输出）。 |
| **截断逻辑** | Rerank 后取 Top-K 直接作为上下文。 | Rerank 后取 Top-K 子块，**丢弃子块内容**，仅提取它们的 `parent_id` 去拿大块文本。 |
| **语义颗粒度** | 检索和生成的颗粒度是**一致的**。 | 检索和生成的颗粒度是**解耦的**（小检索，大生成）。 |
| **最大优势** | 实现简单。 | **抗噪声能力极强**。即使 Rerank 把某个子块排第1，拿到的也是完整父章节，包含了该子块的前后文，不易断章取义。 |

#### Rerank 阈值设定与陷阱

- **不要用绝对阈值（如 >0.5）**：Rerank 的分数分布极度依赖模型和领域。建议**始终采用相对阈值**，即**取分数最高的前 K 个**（如 Top-20 子块）。
- **警惕"高分低质"的孤立子块**：假如某个子块 Rerank 得了满分0.99，映射回父块后，父块有2000字，其中只有那100字相关。**必须接受这一点**，因为多粒度模式宁可给大模型多喂点无关的上下文，也坚决不能把最关键的上下文切丢。这是"召回率优先"策略下的合理取舍。

**最终 RAG 流水线**：
```
Query → 向量检索(取 Top-100 子块) → Rerank(重排子块取 Top-20) → 提取 parent_id 映射父块 → 按原文排序拼接父块 → LLM 生成
```

### 3.2 科学的评估体系

没有度量，就无法优化。科学的评估体系是 RAG 系统优化的基石，其核心是 **"指标驱动"**。

1. **构建高质量测试集（Golden Dataset）**：这是评估的起点。需要准备一个包含 **"问题-标准答案-相关文档ID"** 三元组的标注数据集，它是衡量一切的"金标准"。建议标注 **100个左右** 的问题-标准答案对。
2. **分模块、多指标评估**：不要只看最终答案，要将系统拆解为**检索**和**生成**两大模块，并使用不同的指标分别评估。
3. **离线评估与在线监控结合**：
   - **离线评估**：在系统上线前，利用测试集自动化运行评估，快速验证每一次优化迭代的效果。
   - **在线监控**：系统上线后，持续监控真实用户场景下的业务指标（如任务完成率、用户满意度），发现潜在问题。
4. **持续迭代**：建立"**评估 → 分析 → 优化**"的闭环，让每一次改动都有数据支撑。

### 3.3 RAG 量化指标

RAG 的量化指标可以分为**检索指标**和**生成指标**两大类。

#### 检索指标（评估"找得准不准"）

这些指标专注于衡量检索模块的性能。

| 指标 | 核心问题 | 简要说明 |
| :--- | :--- | :--- |
| **召回率 (Recall)** | **找全了吗？** | 衡量检索到的相关文档占所有相关文档的比例。**粗排优化的核心指标**。 |
| **精确率 (Precision)** | **找得准吗？** | 衡量检索结果中真正相关的文档占比。**精排优化的核心指标**。 |
| **平均倒数排名 (MRR)** | **第一个对的排第几？** | 衡量第一个正确答案在结果列表中的排名，排名越靠前，分数越高。 |
| **平均精度均值 (MAP)** | **整体排序好不好？** | 综合考虑所有相关文档在结果列表中的排序位置，衡量整体排序质量。 |
| **归一化折损累积增益 (nDCG)** | **排序质量高吗？** | 考虑结果排序和相关性分级（如高度相关、部分相关）的评估指标。 |

#### 生成指标（评估"答得好不好"）

这些指标专注于衡量最终答案的质量。

| 指标 | 核心问题 | 简要说明 |
| :--- | :--- | :--- |
| **事实一致性 (Faithfulness)** | **有根据胡说吗？** | 衡量生成的答案是否忠实于检索到的上下文，有无"幻觉"。 |
| **答案相关性 (Answer Relevance)** | **答非所问了吗？** | 衡量生成的答案是否直接、完整地回答了用户的问题。 |
| **上下文相关性 (Context Relevance)** | **给的资料对吗？** | 衡量检索到的上下文信息本身是否与问题相关。 |
| **BLEU / ROUGE** | **和标准答案像吗？** | 通过 n-gram 匹配计算生成答案与参考答案的相似度。 |

## 四、总结

提升 RAG 召回率是一个系统工程，其优化路径可以清晰概括为：

1. **打好地基**：清洗数据，按语义边界动态分块，构建父子块多粒度索引，选对 Embedding 模型，完善元数据。
2. **精准定位**：改写查询，采用"向量+关键词"的混合检索，合理设置 Top-K。
3. **优中选优**：引入 Reranker 模型对召回结果进行精排，在多粒度模式下对子块 Rerank 后映射父块。
4. **持续改进**：建立评估体系，用数据驱动迭代。

一个可参考的实战路径是：**基线（纯向量检索）→ 更换优质 Embedding 模型 → 增加混合检索 → 加入重排序（Rerank）→ 建立评估体系持续迭代**。有案例表明，遵循这一路径，召回率可以从78%逐步提升至92%。

需要注意的是，具体优化策略需要根据你的业务场景、数据特点和延迟要求来灵活选择和调整。
