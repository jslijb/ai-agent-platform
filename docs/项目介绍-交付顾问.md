# 金融智能体平台 — 项目介绍（交付视角）

> 本文档以"交付顾问"视角，完整呈现一个金融行业 AI Agent 平台从需求拆解、方案设计、技术实施到评估验证的全过程。覆盖业务场景、架构设计、交付物清单、技术深度与验证结果，确保客户、售前、交付三方均可据此对齐。

---

## 一、项目定位与客户痛点

### 1.1 项目定位

**金融行业智能体平台**（ai-agent-platform）是一套面向券商、资管、银行等金融机构的 AI 智能体解决方案，核心能力覆盖智能投研、量化分析、合规审查、知识管理四大业务场景。平台基于 Next.js 14 全栈架构，集成 RAG 检索增强生成、GraphRAG 知识图谱推理、多 Agent 协作、MCP 工具协议，为金融机构提供从文档入库到智能问答、从数据查询到风险控制的端到端能力。

### 1.2 客户痛点拆解（业务场景映射）

在交付前期与业务方对齐时，我们识别出金融客户在 AI 落地过程中普遍存在以下五类痛点：

| 痛点类别 | 客户原话（典型） | 根因分析 | 平台对应能力 |
|:---|:---|:---|:---|
| 数据孤岛 | "我们的研报、年报、法规散在不同系统，查一个指标要翻 5 个文档" | 文档非结构化、无统一检索入口 | RAG 混合检索 + 知识图谱 + 文档全生命周期管理 |
| 合规红线 | "AI 直接给客户推荐股票，监管来了谁负责？" | 缺乏意图识别与合规拦截层 | 三级意图识别（Safe/Controversial/Unsafe）+ 合规日志 + 人工审核阈值 |
| 数据准确性 | "AI 回答的营收数字和我们年报对不上，差几个亿" | 测试集数据来源不明、评估指标缺失 | 评估体系（15 指标）+ 数值差异标注 + 人工核查机制 |
| 知识时效 | "研报过期了还在被引用，客户投诉" | 无文档过期管理 | 按文档类型自动过期（研报 90 天 / 年报 365 天 / 法规永不过期） |
| 系统可用性 | "模型一挂全挂，用户全在投诉" | 单点依赖、无降级链 | 多模型降级链 + 熔断器 + 语义缓存 + HNSW→顺序扫描降级 |

## 二、解决方案架构

### 2.1 整体技术架构

平台采用 **"前端 + 主服务 + 微服务 + 数据层"** 四层架构，通过 Docker Compose 编排 11 个服务，实现完整可观测性。

```
┌─────────────────────────────────────────────────────────────┐
│  前端层（Next.js 14 + Tailwind + recharts）                  │
│  15 个页面：对话/文档管理/评估/错题本/记忆/日志/Token 用量    │
│  + 移动端小程序（Taro，5 页面）                              │
└──────────────────────────┬──────────────────────────────────┘
                           │ SSE 流式 + REST API
┌──────────────────────────▼──────────────────────────────────┐
│  主服务（Next.js Route Handlers，:3000）                     │
│  20+ API 模块：Agent/Document/RAG/Evaluation/Auth/MCP...    │
└──────────────────────────┬──────────────────────────────────┘
                           │ ServiceAdapter 路由
┌──────────────────────────▼──────────────────────────────────┐
│  微服务层                                                    │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐            │
│  │llm-     │ │rag-     │ │eval-    │ │data-    │            │
│  │gateway  │ │service  │ │uation   │ │service  │            │
│  │:3002    │ │:3001    │ │:3003    │ │:8001    │            │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘            │
│  ┌─────────┐ ┌─────────┐                                    │
│  │Embedding│ │Reranker │  BGE-M3 + BGE-Reranker-v2-m3       │
│  │:8011    │ │:8010    │                                    │
│  └─────────┘ └─────────┘                                    │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│  数据层                                                      │
│  PostgreSQL(pgvector) + Redis + Neo4j + Prometheus/Grafana  │
│  17 张表，含向量索引(ivfflat/HNSW)、合规日志、四层记忆        │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 关键技术决策（交付时向客户解释"为什么这么选"）

| 决策点 | 选择 | 交付理由（客户视角） |
|:---|:---|:---|
| 向量数据库 | pgvector 而非 Milvus | 架构简化，百万级数据内性能足够，降低运维成本 |
| ORM | Drizzle 而非 Prisma | 原生支持 pgvector + 无影子库权限问题 |
| LLM 提供商 | 阿里百炼而非 OpenAI | 数据合规（数据不出境）+ 中文能力 + 成本优势 |
| Agent 框架 | LangGraph 而非自研 | 状态图 + Function Calling 原生支持，降低维护风险 |
| 工具协议 | MCP + ToolRegistry 双轨 | 内部高性能调用 + 外部标准化接入，兼顾效率与开放 |
| 检索策略 | 混合检索 + Reranker 分离精排 | 稠密+稀疏互补解决召回，精排解决精度 |
| 缓存 | Redis 而非 PG | 延迟 <1ms + TTL + 原子计数，支撑高频查询 |

> 上述决策均有 ADR（架构决策记录）归档，共 10 份，便于交付后客户团队接手维护。

### 3.2 RAG 检索增强生成系统（核心交付价值）

**检索流程**：
```
Query → 同义词扩展 → HyDE 假设文档嵌入（可选）
  → 并行检索: 稠密(pgvector) + 稀疏(BM25) + 图谱(多跳)
  → RRF 融合(K=60)
  → 分离精排: 文档 top5 + 图谱 top3
  → 引用注入 → 返回带来源 Top-K
```

**模块清单（20 个子模块）**：

| 子模块 | 功能 |
|:---|:---|
| 稠密检索 | pgvector 余弦相似度 + HNSW→顺序扫描降级 |
| 稀疏检索 | nodejieba 中文分词 + BM25 + 同义词扩展 |
| 混合检索 | RRF 融合 K=60 |
| 精排 | BGE-Reranker-v2-m3（失败降级原始排序） |
| 知识图谱 | 实体提取 + Neo4j 图谱构建 + 多跳推理 |
| HyDE | 假设文档嵌入查询改写 |
| 语义切片 | 800 字符 + 128 重叠 + 句子边界 + 多级断点 |
| 父子文档 | 父 chunk 扩展，保留上下文 |
| 文本清洗 | 控制字符/页眉去重/全半角/Unicode NFC |
| 引用溯源 | 来源注入 + 来源追踪 |
| 增量更新 | CDC 变更监听 + 增量嵌入 |
| 多模态 | PDF 解析 + 表格提取 + 图片描述 |
| 知识过期 | 按类型自动过期（研报 90 天 / 年报 365 天 / 法规永不过期） |

### 3.4 合规与风控（金融行业交付的核心门槛）

**三级意图识别层**（在检索前拦截，符合金融法规要求）：

| 风险等级 | 问题类型 | 关键词示例 | 处理方式 |
|:---|:---|:---|:---|
| Unsafe | 对抗性 | 预测股价、操纵市场、内幕消息、老鼠仓、洗钱 | 不检索，直接拒绝 + 违法警示（《证券法》）+ 风险提示 |
| Controversial | 投资建议 | 该不该买/卖、抄底、定投、推荐 | 检索财务数据 + 合规拒绝 + 标准化数据参考 |
| Safe | 事实查询 | 营收、利润、技术指标 | 正常 RAG 检索 |

**合规日志系统**（满足监管留存要求）：
- `compliance_logs` 表：记录所有 Controversial/Unsafe 级拦截
- 字段：用户ID（脱敏）/输入内容（脱敏）/风险等级/违规类型/处理动作/输出内容/是否触发人工审核
- **人工审核阈值**：同一用户 24 小时内 Unsafe 级 ≥3 次，自动标记 `triggeredManualReview=true` 并告警
- **保存期限**：不少于 5 年，不自动删除

**监管依据**（交付时向客户合规部门出示）：
- 《证券投资顾问业务暂行规定》（证监会公告〔2020〕66号）第十六、十九、二十八、三十二条
- 《生成式人工智能服务管理暂行办法》第十四、十五条
- 《关于银行业保险业人工智能安全开发应用的指导意见》（国家金融监督管理总局，2026年6月）第十七、二十一、二十二、二十四、二十五、二十九条

## 六、项目深度与交付能力体现

### 6.1 Agent 底层逻辑（向客户证明技术深度）

**ReAct 循环 + 反思 + 工具编排**：
- 标准的 Reason→Act→Observe 循环，最多 3 轮反思式检索
- 重复调用检测：连续 2 轮重复工具调用强制输出，避免死循环
- 幻觉检测：数字无 Observation 支撑则触发再检索
- 确定性输出：temperature=0 + seed=42，保证结果可复现

**多 Agent 编排**：
- Orchestrator 路由：根据 query 分发到 research/quant/compliance/general/skill
- 嵌套编排：综合诊断 = 技术分析 + 合规检查 + 风控评估并行
- 错误恢复：retry/fallback/abort 三策略

**工具检索增强**：
- ToolVectorRetriever：工具语义检索，避免 21+ 工具全量注入 prompt
- ToolDescriptionEnhancer：工具描述增强
- FewShotInjector：FewShot 示例注入

## 七、交付经验总结

### 7.1 成功经验

1. **合规优先**：金融行业交付，合规是第一门槛。意图识别层 + 合规日志 + 人工审核阈值，是获取客户信任的关键。我们在 V11 才补全这一层，前期 V1-V10 在合规上走了弯路，建议后续项目第一版就内置合规层。

2. **评估驱动**：没有量化评估的交付都是耍流氓。15 个指标 + 130 条测试集 + 数据来源标注，让客户清楚知道系统能力边界在哪里。

3. **数据先行**：知识库数据覆盖度 50% 是重大失误。后续项目应在评估前强制验证数据覆盖 100%，数据缺失必须补数据，不允许用 canAnswer=false 掩盖。

4. **降级设计**：金融系统对可用性要求极高。多模型降级链 + HNSW→顺序扫描降级 + 精排失败降级粗排，保证单点故障不致命。

### 7.2 踩坑教训

1. **架构图与实现脱节**：V10 前架构图画了精排，但 Agent 代码实际跳过了精排，只有 API 路由用了精排。交付时要确保架构图与代码一致，避免客户发现后信任崩塌。

2. **测试数据编造**：早期测试集 expectedAnswer 数值是编造的，与知识库文档实际数据不一致，导致 AI 答对了反而被判错。测试数据必须从真实文档提取，标注来源。

3. **metadata 字段丢失**：文档入库时丢弃了分块器生成的 metadata（页码、来源），导致前端无法展示来源、PDF 跳转失效。这类"字段丢失"bug 要通过代码审查及早发现。

4. **PowerShell 与 Docker 兼容性**：Windows 路径在 Linux Docker 容器中报错；PowerShell 不支持 `&&` 分隔符；`drizzle-kit push` 需要 TTY 终端。跨平台交付要注意环境差异。
