## 一、项目概述

**AI 金融分析 Agent 平台**——用户通过自然语言提问，Agent 自主调用工具获取行情数据、计算技术指标、检索研报文档、检查合规性，最终给出有数据支撑的分析结论。

**核心价值**：将金融分析师的日常工作（查数据→算指标→写报告→合规审查）自动化，同时严格遵守《证券法》不提供投资建议。

## 二、技术栈及选择理由

| 层级 | 技术 | 选择理由 |
|------|------|---------|
| **前端** | Next.js 14 (App Router) | SSR+SSG混合渲染，API Routes同构，TypeScript全栈统一 |
| **后端** | Next.js API Routes + FastAPI | Next.js处理Agent逻辑（TypeScript生态），FastAPI处理数据服务（Python生态，pandas/numpy金融计算） |
| **数据库** | PostgreSQL + pgvector | 关系数据+向量检索统一，pgvector HNSW索引支持高效相似度搜索，避免引入独立向量库 |
| **缓存** | Redis | 限流滑动窗口、熔断器状态、LLM缓存、Checkpoint存储，一库多用 |
| **向量嵌入** | BGE-M3 (本地部署) | 多语言支持好，金融领域表现优，本地部署无API成本 |
| **重排序** | BGE-Reranker-v2-m3 (本地部署) | 与BGE-M3配套，精排提升检索精度 |
| **知识图谱** | Neo4j | 实体关系存储，路径查询补全向量检索盲区 |
| **LLM** | 阿里百炼(DashScope) + AGNES | 降级链保证可用性，百炼为主力，AGNES为备选 |
| **容器化** | Docker Compose + Nginx | 一键部署，nginx统一入口，容器间网络隔离 |
| **认证** | NextAuth v5 (JWT) | 轻量级，无服务端session存储，适合容器化部署 |
| **ORM** | Drizzle ORM | TypeScript原生，类型安全，轻量（比Prisma轻10倍） |

## 四、项目优点（面试亮点）

### 4.1 架构设计优点

**1. 工具合并策略（21→6），解决LLM工具选择困难**
- 问题：21个工具的JSON Schema约4000 token，LLM选择准确率低
- 方案：按功能内聚合并为6个（技术分析/风险分析/合规检查/行情数据/工具搜索/混合检索）
- 效果：token减少60%，合并工具自动获取数据减少调用轮次

**2. 三层错误恢复，保证金融分析不中断**
- Checkpoint+Resume：每轮保存进度到Redis，失败从断点恢复
- LLM降级链：模型A故障自动切换B/C
- 工具验证重试：参数校验失败让LLM修正最多3次

**3. 合规护栏，法律刚需**
- 三级意图分类（Unsafe/Controversial/Factual）
- Unsafe直接拒绝+引用《证券法》
- 拦截日志保存5年，24h内3次Unsafe触发人工审核

**4. 4层记忆架构，跨会话信息不丢失**
- L1最近对话/L2滚动摘要/L3历史片段/L4用户画像
- 金融数值在压缩时保留原始精度
- 灵感来自MemGPT，按token预算动态分配

**5. 两阶段RAG管线，金融场景最佳实践**
- 粗排：稠密pgvector + 稀疏BM25 → RRF融合
- 精排：bge-reranker API
- 图谱补充：Neo4j路径查询补全向量检索盲区
- 精排失败自动降级为粗排截取

### 4.2 工程实践优点

**6. 完整容器化，一键部署**
- Docker Compose编排，nginx统一入口
- 复用已有postgres/redis，减少资源开销
- .env.local不挂载到容器（避免AUTH_URL端口冲突）

**7. 完整评估体系**
- RAG 4维度 + Agent 5维度评估
- 开放数据集适配器（CFLUE/FinEval）
- 当前基线V13-r6综合0.9153

**8. 可观测性**
- 6种步骤类型，毫秒级耗时追踪
- 前端StepCard实时展示Agent推理过程
- Agent日志写入数据库供后续分析

### 4.3 诚实面对不足

**9. 知识图谱数据质量待提升**
- 当前602个节点，关系类型都是RELATION（太笼统）
- 实体没有type标签（公司/地点/金额混在一起）
- 需要优化entity-extractor的prompt和图谱schema

**10. LLM缓存是精确匹配，不是语义缓存**
- 名称有误导，实际只缓存完全相同的请求
- Agent场景下命中率低（每轮messages都不同）

## 五、数据流（一次完整查询）

```
用户："招商银行MA20和RSI怎么样？"
  │
  ├─ [合规护栏] classifyIntent → Factual（放行）
  │
  ├─ [ReAct循环] 第1轮
  │   ├─ LLM决定调用 technicalAnalysis({stockCode:"600036",indicators:["MA","RSI"]})
  │   ├─ 工具执行：fetchStockData("600036") → 计算MA20/RSI → 返回结果
  │   └─ [Checkpoint] 保存进度到Redis
  │
  ├─ [ReAct循环] 第2轮
  │   ├─ LLM获得工具结果，有足够信息
  │   ├─ [反思] shouldRetrieveAgain → needMore=false（数据充分）
  │   └─ LLM输出最终答案（含数据来源标注）
  │
  ├─ [流式输出] SSE推送每步过程到前端
  │
  ├─ [记忆更新] addMessage + 更新updatedAt + 异步生成摘要
  │
  └─ [日志保存] saveAgentLog（步骤+耗时+token用量）
```

## 六、关键设计决策

| 决策 | 选择 | 备选 | 理由 |
|------|------|------|------|
| Agent范式 | ReAct | Plan-and-Execute | 金融分析步骤少且依赖前步结果，ReAct更灵活 |
| 向量数据库 | pgvector | Milvus/Qdrant | 与PostgreSQL统一，运维简单，HNSW索引够用 |
| 记忆架构 | 4层MemGPT式 | 单层对话历史 | 金融对话跨会话，需要长期记忆 |
| 工具策略 | 合并(21→6) | 保持细粒度 | 减少token+提高选择准确率 |
| 缓存策略 | 精确匹配 | 语义缓存 | 语义缓存需要额外embedding计算，ROI不高 |
| 认证策略 | JWT | 服务端Session | 容器化部署无状态，JWT更适合 |
| 部署方式 | Docker Compose | K8s | 单机部署，K8s过重 |
